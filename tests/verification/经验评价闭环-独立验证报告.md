2. **新经验具有中性先验**：`n_eff=0 → quality_signal=0、trust=0.5`（§33）。**通过**。
3. **证据强度随样本增加饱和**：`n_eff` 从 0 到 40 逐步长全量复算，严格单调递增、始终 <1；`evidence(40)=0.9932620530009145`、`evidence(8)=0.6321`、`evidence(16)=0.8647`；40→50 的增量 < 0→10 增量的 1/10。**通过**。
4. **评分波动降低 Stability**：+1/−1 交错 → `variance=1 → stability=0`；而 4 次一致的满分 → `stability=1`。**通过**。
5. **Evaluation 可以完全重放**：见 §4.3（真实库上的增量↔重建逐字段一致 + 注入标记聚合器证明重算而非复制）。**通过**。

### 2.3 召回复算（§17 / §19 / §20）

**有界信任修正**：`sim01` 归一化（含 ±越界夹回）、`adjusted = sim01 × (1 + 0.2q)` 在 `q∈{−1,−0.5,0,0.5,1} × cosine∈{0,0.5,1}` 共 15 组上逐值相等；相对影响 `|adjusted−sim01|/sim01` **全部 ≤ 0.2**（实测 `q=1,cos=1 → 1.2`；`q=−1,cos=1 → 0.8`）。**通过**。

数学边界（我推导 + 数值验证）：由于 `|quality_signal| < 1` 恒成立（`empirical<1`、`evidence≤1`、`0.5+0.5×stability≤1`），实际影响严格小于 ±20%。低相关高信任击败高相关的充要条件是 `sim01_L/sim01_H > 1/1.5 ≈ 0.6667`，即「明显更相关」必须至少高出归一化相似度的 50%。**这一点源自 §17 的 `sim01=(cos+1)/2` 口径，不是实现偏差**——需注意 `cosine∈[−1,0]` 被压缩到 `sim01∈[0,0.5]`，因此「正交（cosine=0）」的经验仍拿到 0.5 的基准相关性，最高信任下为 0.6。

**MMR**（`relevance_weight=0.40 / diversity_weight=0.60`，手算）：
- 首轮（已选集为空 → 多样性项为 0）：A/B 重复族 `cos=0.8 → adjusted=0.9`，C 正交 `cos=0.4 → adjusted=0.7`；`0.4×0.9=0.36 > 0.4×0.7=0.28` → 选 A（同分按 id 升序）。**通过**。
- 第二轮：`mmr(B) = 0.4×0.9 − 0.6×1 = −0.24`；`mmr(C) = 0.4×0.7 − 0.6×0.5 = −0.02` → 选 C（全重复族的 B 被压下去）。**通过**。
- **diversity 项完全不吃 Trust**：把 B 的 `qualitySignal` 从 0 改为 −1，`pairSimilarity(B,A)` 仍为 1，第二轮结果仍为 C；`pairSimilarity` 只吃两侧向量。**通过**。
- 高信任 + 高重复 3 条 `q=1` 时，第 2 位仍是正交的低信任候选 —— 高信任不能霸占列表。**通过**。
- 最终命中的 `score` = `adjustedRelevance`（不含 MMR 多样性项）。**通过**。

**语义 Top-K 边界（§36「只能在 semantic Top-K 内重排」）**：我构造 40 维受控向量：30 条池内经验（cosine=0.5，`qualitySignal=0`，`adjusted=0.75`）+ 5 条池外经验（cosine=0.49，各 16 次满分评价 → `qualitySignal=0.728139`，`adjusted=0.853493`）。池外经验修正后相关性**严格高于**池内任何一条，但 `recall(topK=50)` 返回**恰好 30 条且不含任何池外 id** —— 证明信任无法把语义候选池之外的候选拉进有界重排。**通过**。

- 无评价历史的经验在重建后等于 `{...NEUTRAL_STATS, recalledCount}`，且 `aggregateExperienceStats({evaluations: [], recalledCount})` 与之**深相等** → 证明 `rebuildStatsRows` 里「无历史直接写 neutralStats、有历史才调 aggregate」这条分支与「一律调 aggregate」在域层入口上是**等价**的（Lead 复核点 5 前半）。

### 4.2 重建确实重算而非复制

`store.rebuildStats()` 接受调用方注入的聚合器（`ExperienceStatsRebuildInput.aggregate`）。我注入一个「标记聚合器」（返回 `empiricalValue=0.123, trust=0.456, usedCount=0`），重建后读回正是标记值 → 重建**按注入的聚合器重放历史**，而不是复制旧行。随后 `service.rebuildStats()` 恢复正常聚合器，统计行逐字段回到修复前的正确值 → 证明 §35「Stats 更新失败后可经 rebuild 修复」。

### 4.3 使用事实的增量语义（Lead 复核点 5 后半）

- 已有统计行时再记录使用：`recalled_count` 由 1 → 2，其余列一字未变（实测 `toEqual({...shape(first), recalledCount: 2})`）。
- **`updated_at` 不刷新**：用推进时钟实测 `usage#1 updated_at=7000`、`usage#2 updated_at=7000`（此刻时钟已到 `10000`）、随后 `feedback` 使其变为 `10000`。即使用事实的增量确实不刷新记账时间（缺陷 D3）。
- 与「完全重放」的关系：增量路径聚合时用的 `recalledCount` 取自**统计投影**（`experience-evaluations.ts:79` → `readRecalledCount`），重建取自**使用事实表**（`assets/experience-stats.ts:209` → `COUNT(*)`）。我按「每次使用要么建行、要么累加」「统计行只由评价路径与重建整表覆盖」两条不变量逐路径核对，并实测多经验多使用场景下两者一致 → **在统计投影完整的前提下两者等价**；唯一可能分叉的路径是人为删除/损坏统计行（无公开写路径），届时 `rebuild` 会以使用事实为准修复。**结论：等价，但增量侧读的是投影而非事实表，属可维护性隐患而非当前缺陷**（见 D3 建议）。

### 4.4 §35 四条失败隔离（全部由我构造失败端口实测）

| 隔离项 | 实际行为（实测） | 判定 |
|---|---|---|

**「增量与重建的 `updated_at` 不同」是否构成真实缺陷？我的判据与结论：不构成。** 三条判据：

1. **契约面**：§22 规定统计行是「**可重建的派生投影**」，§24/§25 要求的「完整重放」对象是**统计值**（`empirical_value / evidence_strength / stability / quality_signal / trust / harm_* / counts`）；`assets/AGENTS.md` 明确「时间戳一律 epoch 毫秒，**由本模块记账**」「`updated_at` 每次写入刷新」。重建对每一行都执行了写入 → 取其自身的写入时刻，正是该规则的要求。
2. **消费面**：我在 `src/` 全域检索 `stats.updatedAt`，除统计行的读取/写入管道本身外**没有任何消费点**；GUI 展示的六项统计（`client/lib/experience-stats.ts` 的字段闭集）**不含 `updated_at`**。因此该差异对信任、召回、界面均零影响。

### 14.3 改动 3：`description.length < 3400` 是否属于「拍脑袋阈值」（判定：**不属该问题，应保留**）

对照 §20 拒绝硬编码 `semantic_floor` 的理由，我给五条判据：

1. **类别不同（决定性判据）**：§20 拒绝的是**分割真实数据分布的行为参数**——`semantic_floor` 的取值决定"哪些经验被挡在重排之外"，其正确值是相似度分布的函数，未经验证的绝对值会造成**静默排除**（永久挡掉确有价值但相关的经验，且无从发现）。而 `3400` 度量的是**固定源码文本的长度**，被度量对象不是运行时数据、没有分布可校准 —— "用数据验证"在范畴上不适用；它本质是**预算式不变量**，数字是选择出来的，不是测出来的。
2. **失败模式相反**：护栏失败是响亮且全量的（测试红，迫使人在"压缩文本"与"调高预算"之间显式裁决）；§20 担心的正是静默降级。它不会像 floor 那样"悄悄少召回几条"。
3. **无"合法输入被误杀"的空间**：description 的内容是随代码发布的常量，与外部数据无关；唯一会让它失败的是**有意往里面加文本**，而这正是它要拦住的漂移（R2① 的关切）。它不改变任何输出语义，也不参与任何判定。
4. **仓库既有范式**：`wf-ask`、`wf-ask-agent`、`wf-db-query`、`wf-finish`、`wf-run-node`、`wf-run-node-wait` 的 tool 测试均已存在 description 的**数值化上限**（如 `split(/\s+/).length <= 130`）——"给 description 设数值预算门"是既定实践，本轮的 3400 与之同型。
5. **反事实**：删掉它，3630 → 3270 的压缩就没有任何回归保护，文本可无阻再次膨胀，且这类膨胀不会让任何其它测试变红。

**结论：保留该断言，不判为缺陷。** 两点改进建议（不阻塞）：①注释补上数字来源与余量（实测 3270 → 上限 3400，余量 130 ≈ 4%），当前注释只写了实测值，后来者无法判断余量是否合理 —— 记为 **R4（信息性）**；②一旦宿主上限被实测确认（R2①），应把该常量改为**由契约推导**（"宿主上限 − 余量"）而不是预算值，届时它连"数字来源"这一条弱点也不存在了。

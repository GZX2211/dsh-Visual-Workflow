## 一、代码核查结论（决定规范能否落地的 5 个事实）

### 1. 角色资产「复用 / 改造 / 新建」三级能力：资产层已实现，但父代理只能驱动「新建 / 复用」，**驱动不了「改造」**

`workflow-assets.ts` 的 `ensureRoleRowForNode`（[workflow-assets.ts:795-841](../src/host/assets/workflow-assets.ts#L795)）按节点内容登记角色版本行：

| 节点状态 | 登记结果 |
|---|---|
| 有 `sourceAssetId` 且内容与该资产 Active 版本全等 | 只登记引用（**复用**） |
| 有 `sourceAssetId` 但内容被改写 | **在该资产下追加新版本**（**改造**，版本链延续） |
| **无** `sourceAssetId`、内容命中已有版本行 | 复用该版本行（跨资产去重） |
| **无** `sourceAssetId`、内容全新 | 新建 `inline` 角色资产（**新建**） |

而 `sourceAssetId` 被 `PARENT_UNCONFIGURABLE_ROLE_FIELDS` **剥离**（[apply.ts:161-175](../src/host/tools/wf-graph-patch/apply.ts#L161)），父代理无法设置；图模型里也没有 `roleAssetId` 字段。

⇒ **父代理改图时"复用已有角色"只有一条路：把 `wf_org_catalog` 召回的 systemPrompt 全文写进新节点的 `data.systemPrompt`**（token 成本 ≈ 读全文 + 写全文；大角色文本还会挤压补丁与上下文窗口）。系统层不会产生重复资产（内容去重），但：
- **无法表达"在这个资产基础上改造"** → 改写后的角色会被登记为新 inline 资产，原资产版本链断裂；
- **自进化闭环在此断裂**：经验/运行反馈驱动的角色改进无法回流到既有角色资产。

### 2. 父代理 → 子代理的「任务发布」通道：official 有，legacy 无

- official（官方 Agent Team 可用）：9 个官方工具注册在**含 Lead 自身**的成员作用域（[protocol.ts:251-263](../src/host/shared/protocol.ts#L251)），父代理可用 `send_message` / `team_task_*` 派任务；
- legacy（官方 Team 不可用）：`wf_ask_agent` 明确只允许**子代理**调用（[runtime-comm.ts:196-198](../src/host/orchestrator/runtime-comm.ts#L196)），父代理没有任何"向子代理发消息"的工具；`wf_run_node` 只接受 nodeId（[wf-run-node/tool.ts:36-41](../src/host/tools/wf-run-node/tool.ts#L36)），不能携带任务文本。

⇒ 规范第 6 点"任务分配都通过 Send Message 完成"在 **legacy 通道无法实现**，是架构缺口（不是提示词能解决的）。

### 3. 子代理 → 父代理的「上报/求决策」通道：official 有（send_message → lead），legacy 无

- `wf_ask_user` 是"子代理借用会话 root 身份向**用户**提问"（[wf-ask-user/tool.ts:142-177](../src/host/tools/wf-ask-user/tool.ts#L142)），父代理不参与中间环节；
- `wf_ask_agent` 的目标只能解析到同 run 的节点子代理（`childIndex` / `childByNode`），**父代理（root）不可达**（[runtime-comm.ts:129-160](../src/host/orchestrator/runtime-comm.ts#L129)）。

⇒ 规范第 7 点"子代理无法决策应汇报父代理，父代理立即响应"在 **legacy 通道无通道**；official 通道可经官方 `send_message(target: "lead")` 实现。

### 4. 「节点可重跑」与现有护栏语义冲突

- `wf_run_node` 对节点状态**没有**"已 ok 不得重跑"的校验，重跑在 mode1 是可行的；
- 但同一节点受 `retryLimit` 护栏：`attempt > effectiveRetryLimit + 1` 抛 `WF_RETRY_LIMIT`（[runtime-execute.ts:131-136](../src/host/orchestrator/runtime-execute.ts#L131)），默认 `retryLimitDefault = 3`（[config.ts:79](../src/host/config.ts#L79)）→ 单个节点最多 4 次启动；
- 全局 `GLOBAL_RUN_CALL_LIMIT = 500`。

⇒ 规范第 5 点"按实际需要调度已完成节点应对新任务"与"重试上限"是**两种语义共用一条护栏**：前者是"重新调度（新任务）"，后者是"失败重试"。需要区分（否则父代理按规范重新调度几次后会被硬拒绝）。

### 5. `wait_agent` 语义与"等待节点产出"不完全对应

官方 `wait_agent` = **等待下一次团队变化**（[protocol.ts:271-272](../src/host/shared/protocol.ts#L271)），不是"等待指定节点完成"；且只在 official 通道存在。规范第 10 点若写成"用 wait_agent 等节点产出与汇报"，与官方语义有偏差，且与现状"异步调度 + 结算通知驱动"存在张力（等待会串行化并行调度）。

附带核查：Team 卡片允许空成员（[graph/model.ts:265](../src/host/graph/model.ts#L265) 默认 `memberIds: []`；校验只查双向一致与幽灵成员，不要求非空）→ 规范第 12 点"空组"在架构上可行 ✅。

## 三、规范内部冲突 / 闭环风险（需你裁决）

1. **第 5 点 vs 重试护栏**：允许重新调度已完成节点，必须区分"新任务重跑"与"失败重试"，否则几次调度后被 `WF_RETRY_LIMIT` 拒绝（默认 4 次/节点）。→ 是否调整护栏语义（代码改动）？
2. **第 6 点 vs 通道现状**：规范写"任务分配都通过 Send Message"，但 legacy 通道不存在该工具。→ 提示词是否先按"通过可用的消息通道"抽象表述，同时把 E3/E4 排入架构任务？
3. **第 10 点 vs `wait_agent` 语义**：官方工具是"等待下一次团队变化"。若写成"等待节点产出"，与实现不符；若真的串行等待，又会牺牲并行调度。→ 需要明确它在提示词中的表述（引导等待"变化"而非"完成"）。
4. **第 2 点"粒度不合适" vs 第 3 点"只改这一步"**：调整粒度往往要**插入/拆分节点**（结构性改动，必然影响后续），与"只改当前一步"存在张力。→ 允许的结构改动边界需要明确（建议：允许在"当前节点→下游节点"之间插入修复/补充节点与条件分支，不允许改动更远的下游）。
5. **第 8 点"部分阻塞时先做无影响任务"** vs run 只有整体终态（running/paused/stopped/failed）：现状没有"部分停止"语义，只能靠父代理编排出"先做完无影响节点、再暂停/终止"。→ 提示词可表达，但需确认这类"部分阻塞"用**暂停**（可恢复）还是**终止**（wf_finish failed）收尾。
6. **第 4 点"核验并纠正子代理"**：纠正走消息通道；但 oracle 侧"越界/超权"的判定标准需要可操作（例如子代理改了不该改的东西、调了不该调的工具、交付偏离 outputSchema）。→ 建议在五维中写成"核验四问"，不引入新的校验机制。
7. **自进化闭环**（重点）：
   - 经验工具与运行解耦（既定案），因此"父代理在收尾是否学习"不由编排提示词强制；但新规范里的高频行为（改图决策、任务分配、阻塞处理）正是 orchestrator 经验的素材 → 建议在五维的交接契约里保留"收尾沉淀"的职责级指引（一句话），不写具体调用流程。
   - **E2 未修的话**：经验驱动的角色改进无法回流资产，"复用→改造→新建"三级中的"改造"链路名存实亡，自进化闭环缺一环。
   - 运行期渐进改图会让 run 快照的图与最终图不一致 → 经验溯源需明确以哪一版为准（现状：run 快照 + `wf_org_catalog` 的 instance 骨架）。

## 四、需要你确认的 6 个决策点（确认后我开始写五维提示词）

1. **承载方式**：新五维文本作为**父代理节点 systemPrompt 的默认值/播种**（新建父代理节点时写入，用户可改），对吗？
2. **E1/E2（资产复用与改造闭环）**：是否要新增"按角色资产 id 复用/改造"的补丁能力（本轮只记录，还是排入实现）？
3. **E3/E4（legacy 通道缺口）**：提示词先按"可用通道"抽象表述 + 架构排期，还是本轮一并补通道？
4. **E5（重跑护栏）**：是否调整 `retryLimit` 语义（区分重跑与重试）？
5. **第 3 点的结构改动边界**：是否接受"允许在当前节点与下游之间插入节点/条件分支，不得改动更远下游"这一约束？
6. **第 13 点 Team 规划判据**：保留在可召回规则段（现状），还是同时写入父代理 systemPrompt 一句职责级原则？

## 0. 术语速查（冷启动必读）

| 术语 | 含义 |
|---|---|
| 协作组（group） | 画布上一种节点（kind=group），卡片内并行启动多个成员（`data.memberIds`）；成员间可用 `wf_ask_agent` 互发消息 |
| 节点子代理（node subagent / child） | 每个角色节点（agent）启动时创建的子代理，即该节点的执行者 |
| childId | 节点子代理的**会话 id**，运行期随机 UUID（如 `bb5d4e5a-...`），子代理创建时生成 |
| nodeId | 节点在工作流中的**固定 id**（如 `agent-mtegbjaf-58uc`），画布拓扑里可见、协作块里列出 |
| childIndex | 编排运行时的内存表：childId → { sessionId, flowId, nodeId }（`runtime-base.ts`），节点启动时登记，运行销毁时清空 |
| childKey | 子代理复用键 = `sessionId:flowId:nodeId`（`runner.ts childKey`）；同一节点重跑复用同一子代理 |
| wf_run_node | 父代理启动节点子代理的工具（模式一异步、模式二阻塞）；运行时可对同一节点多次调用（重试/续跑） |
| wf_ask_agent | 组内成员阻塞通信工具（ask/reply/resolve 三态）；**目标寻址**：`targetChildId`（ask 填目标、reply 填发起者） |
| setNodeStatus | 快照节点状态写入函数（`orchestrator/snapshot.ts`） |
| handleSubagentEnd | 子代理结束事件回写（`orchestrator/runtime-observe.ts`）：completed→节点 ok，否则 fail |
| markGroupOkIfComplete | 协作组成员全部 ok/react-capped 时把组卡片标记 ok（仅回显，不干预父代理调度） |
| 模式一 / 模式二 | mode1=编排执行（父代理异步调度）；mode2=后台服务（阻塞式请求流） |
| 父代理 | 会话根 Agent，即“编排调度者”，用 wf_run_node 启动节点、用 wf_finish 收尾 |

**协作组理想流程（需求设计）**：成员并行启动 → 开发侧完成后 `wf_ask_agent(cmd:'ask', targetChildId:<审查成员>)` 通知 → 审查成员（含“待命/冷态”）被唤醒执行审查 → `wf_ask_agent(cmd:'reply', ...)` 回传 → 开发按“通过/不通过”处理。

## 4. 待跟进问题清单（本次复盘核心）

> 每一项均给出：现象（含当次证据）→ 代码位置 → 根因 → 影响 → 建议方案。
> 优先级：P0=影响协作正确性认知/历史可信度；P1=影响重跑与效率；P2=诊断/性能/流程细节。

### P0-1 待命成员被误判为“终态完成”，组卡片提前 ok

- **现象**：审查专家按设计“激活后待命”，但待命回合一结束，`handleSubagentEnd` 即把节点回写为 **ok/终态**；随后组卡片在 15:51:32 被标记 ok（“全部成员已完成”），而实际“通知→审查→修复→复查→交付确认”循环直到 16:02 收尾前才闭环。
- **代码位置**：
  - `src/host/orchestrator/runtime-observe.ts`：`handleSubagentEnd`（completed → 节点 ok，输出=最后一条 assistant 文本）；`markGroupOkIfComplete`（组内全部成员 ok/react-capped 即组 ok，注释注明“只回显，不干预父代理调度”）。
- **根因**：节点状态模型把“成员某回合结束”等同于“成员完成”；协作组内“待命（可被唤醒）”这一中间态在快照/状态机上没有表达。
- **影响**：运行历史、UI 回显、以及任何按节点状态做判定的消费方（如断点续跑“已 ok 节点不重跑”）可能把待命成员误当完成；组卡片完成时间早于真实协作完成。
- **建议方案**（任选或组合）：
  1. 成员节点引入「armed/待命（可唤醒）」中间态，明确区别于终态 ok；待命回合与真实产出回合可区分。
  2. 组卡片 ok 的判定叠加“该组当前**无挂起/超时的 ask**（`RunEntry.asks` 中涉及该组）且全部成员至少有一次 ok 回合”的条件，避免协作进行中即显示组完成。
  3. 由于协作完成最终由父代理 `wf_finish` 判定，可评估让组 ok 由父代理显式声明（或保持“仅回显”并降低其语义权重）。

### P0-2 成员多回合复用时，快照 `endedAt` 冻结、`output` 被覆盖 → 记录自相矛盾

- **现象**（直接来自运行快照）：
  - 审查专家：`endedAt = 15:21:49`（首次待命回合），但 `output` = 复查报告（≈16:00 回合）。
  - 开发工程师：`endedAt = 15:32:28`（恢复后的回合），但 `output` = 最终交付确认（≈16:00 回合）。
- **代码位置**：`src/host/orchestrator/snapshot.ts` `setNodeStatus`——ok/react-capped 时 **output 每次都被覆盖**（约 L114-116），而 `endedAt` 仅在**首次**为空时写入（约 L120 `if (!entry.endedAt)`）。
- **根因**：`endedAt` 语义是“首次完成时间”（冻结），output 是“最近一次完成输出”——对会被多次唤醒续跑（followup 多回合）的成员，两者时间轴错位。
- **影响**：运行历史/审计中“结束时间 < 最终输出产生时间”，排查时误导；未来若按 endedAt 做生命周期/清理会出错。
- **建议方案**：
  1. 把 `endedAt` 语义定为“最近一次完成时间”并持续刷新（注意检查既有测试/续跑逻辑对 endedAt 的依赖）。
  2. 更彻底：为可续跑节点在快照结构中记录**回合明细**（如 `turns: [{ startedAt, endedAt, stopReason, outputSummary? }]`）。若改动 node 记录结构（涉及 `shared/types.ts`），按 AGENTS.md 需同步 `docs/架构文档.md` 并跑 `pnpm typecheck`。

### P1-3 节点“重跑”为续跑旧对话而非干净重跑，且重复整段汇报

- **现象**：开发工程师第一次执行被用户手动停止后，父代理再次 `wf_run_node` 返回**同一 childId**（快照 attempts 1→2），子代理复用原会话、随后**整段重复**了与前一次几乎相同的完整报告（token/上下文浪费）。
- **代码位置**：
  - `src/host/agent/runner.ts`：`childKey(sessionId, flowId, nodeId)`（复用键）；`nodeChildren`（Map 复用键→childId/signature）；`ensureNodeChild`（签名不变即复用既有子代理）。
  - `src/host/orchestrator/runtime-execute.ts`：重跑时重新 `childIndex.set` 同一 childId、`attempts +1`。
- **根因**：节点子代理“一次创建、多次唤醒”的复用设计，与用户对“重启=重新开始”的直觉不一致；且恢复/续跑时没有强制“仅汇报增量”。
- **影响**：重试/重跑时旧上下文会保留（可能污染判断）；报告膨胀（令牌浪费）。
- **建议方案**：
  1. 提供显式 **force-restart** 语义：`wf_run_node({ nodeId, restart: true })` 时清除/nodeChildren 忽略复用键、新建子代理（需评估对官方 subagents 创建既有 childId 的影响）。
  2. 续跑（复用）时在节点任务块动态段（`runContextText` 已有 attempt 计数）追加“本次为恢复执行，请只汇报自上次以来新增/变化的部分”。

### P2-4 协作类错误文案缺少“下一步指向”，成员难以自助纠错

- **现象**：预修复环境下成员连试两次 `wf_ask_agent` 均得到“目标 xxx 不是当前运行的节点子代理”，无法区分“id 填错形式”与“目标真不存在/未启动”，只能求助父代理。
- **代码位置**：`src/host/orchestrator/runtime-comm.ts`（`WF_ASK_TARGET_UNKNOWN` 报错点；即使寻址已修，该码在“目标未启动/未知”时仍会命中）。
- **建议方案**：按情形区分错误并给出可行动指引，例如：
  - 目标 id 不匹配任何成员：列出该成员协作块中的可用成员 id；
  - 目标是本工作流节点但**尚未被调度启动**：提示“该成员可能还未被父代理启动，请稍后重试或请父代理调度”；
  - 向自己发起：提示不可自投。
  （规模小可只在文案上区分；审计日志已存在，可补充字段。）

### P2-5 组内直连失败时全链路退化为“父代理桥接”（串行 + 高上下文消耗）

- **现象**：本次运行中，“通知审查→初查→修复→复查→交付确认”共 5 轮交互**全部由父代理 `send_message` 双向转发**（组内直连失败后的临时兜底）。
- **性质**：不是单一代码 bug，而是**流程缺口**：协作失败缺少文档化、可自动化的兜底协议，父代理只能临场摸索。
- **建议方案**：
  1. 在协作 Prompt（`prompts/collab.ts` 或组 collabPrompt 示例）中写明“组内 `wf_ask_agent` 失败（报 WF_ASK_* 错误）时，应将未完成事项连同文件索引交给父代理转发”的兜底协议，把本次的手工桥接固化为约定。
  2. 父代理编排提示词（`prompts/orchestration.ts`）补充“当收到成员请求转发的组内消息时，按原文转发并在回传后原路送回”的指令。
  3. 可选：`wf_ask_agent` 投递失败（`WF_DELIVERY_FAILED`）时自动重试一次再上抛，降低瞬时失败率。

### P2-6 节点 id 寻址的反查为 O(n) 线性扫描（性能小项）

- **代码位置**：`src/host/orchestrator/runtime-comm.ts` 新增的 `childForNode`（每次 ask 扫描 `childIndex` 全表）。
- **建议方案**：协作组规模较大时，随 `wfRunNode` 登记维护 `nodeId → childId` 反向索引，把每次 ask 的目标解析收敛到 O(1)。当前规模可暂缓。

### P2-7 `attempts` 无法区分失败/用户停止/正常完成（审计小项）

- **现象**：运行快照中开发工程师 `attempts: 2`，但无法看出第 1 次是“用户手动停止”而非内部失败。
- **代码位置**：`RunEntry.attempts`（`nodeId → number`）只计数不记因；快照节点 `attempts` 字段同理。
- **建议方案**：把终止原因（stop / interrupt / fail / react-capped）随回合记入（可与 P0-2 的 `turns` 明细一并设计），使运行历史可回放每一轮发生了什么。

# 规划期发现（第一手编排证据）

> 来源：父代理在**规划工作流模板**过程中的真实遭遇。按本次实验要求，编排过程本身即被测对象，
> 故该发现与后续运行期证据同等有效。

## D-01（P0）数据库节点无法接入任何连线：db 线目标校验与图模型互斥

**现象**
在工作流模板补丁中建立 `database --db-out--> 角色节点[db-in]` 时，补丁被图检查器整批阻断（原子性，未落盘）：

```
[dbLineTargetInvalid] 数据库出线的目标「n-agent-exp」(agent) 不是数据库节点
  → 建议：数据库出线只能连到数据库节点的数据库入点
```

**实际行为 vs 预期行为**
- 预期：数据库节点作为数据源，经 db-out → 角色节点 db-in 注入检索/查询工具（图语义：db 通道不注入内容，
  只把数据源转换为检索/查询工具；`HANDLE_PAIRING` 明确 `db-out → db-in`）。
- 实际：检查器要求 db-out 的目标必须是 database 节点；而 database 在连接点矩阵中 `inputs: []`（没有 db-in），
  把它当目标又会被 `validate.ts` 的 `invalidHandle` 拦下。两条路径互相堵死。

**证据（代码位置）**
- `src/host/graph/model.ts:63`：`database: { inputs: [], outputs: ['db-out'] }`
- `src/host/graph/model.ts:72`：`HANDLE_PAIRING['db-out'] = 'db-in'`
- `src/host/graph/invariants-rules-nodes.ts:159-176`：`ruleDbTarget` 要求 db-out 的目标 `kind === 'database'`
- `src/host/graph/invariants-types.ts:93`：`dbLineTargetInvalid` 级别为 error（阻断落盘）
- 对照：既有模板 `项目开发` / `插件测试` 中存在 `database → agent[db-in]` 连线——那是画布手工保存、
  未经检查器（检查器只约束 `origin='agent'` 的改图），说明该形状在画布侧本就被支持。

**影响**
经检查器的工作流图**无法包含任何 database 节点**：连角色节点被检查器拦；连 database 自身被连接点矩阵拦；
不连线则触发 `orphanNode`（error）。即"数据库数据源"这一整类节点的编排能力被阻断，波及经验库/资产库检索类编排。

**用户裁决（2026-10-10）**
- 定性：**校验器缺陷**——报错文案与判定均错误。正确语义是「数据库出线只能连到**角色节点**的数据库入点」。
- 处置：在本次实验的编排过程中修复，并做回归验证；模板阶段暂不放 database 节点，不阻断整体编排推进。

**修复与回归要点（交给运行阶段，先确认设计方向再动手）**
1. 修正 `ruleDbTarget` 的判定与文案：db-out 的目标应为角色节点（agent / parent / proxy）。
2. 需求确认：database 之间是否需要直连（当前矩阵无 db-in，无法自连）；若需要则须补 db-in 输入点。
3. 回归范围：`tests/host/graph/*`、`tests/host/tools/wf-graph-patch/*`；补两例用例——
   「database → 角色节点 db-in 合法」与「db-out 目标非法（如指向 file/group）」。
4. 最小复现输入：本文件记录的补丁报错原文即可复现（模板 `插件全量工具与编排闭环自修复测试` 的
   database 版本补丁被整批阻断）。

## 对本模板的处置（已执行）

- 模板按裁决**不含 database 节点与 db 线**，保留 24 个节点（3 阶段 + 父代理 + 12 子代理 + 2 文件 + 4 虚拟 + 2 协作组）。
- 数据库能力改为由执行节点用「代码直读 SQLite + 无 db 线时 wf_db_query 的实际行为」取得对照证据，
  并在工具与图编排实测中通过实例改图复现该阻断、留存原始报错。

**落盘结果**：模板 `tpl-23aa312795b8`「插件全量工具与编排闭环自修复测试」，mode1，24 节点 / 56 连线
（flow 17 / ctx 39 / db 0），补丁 80 个 op 一次通过，`warnings: []`。

## D-02（P2）写图契约未覆盖结构校验规则：规划者必须读源码才能保证补丁不被阻断

**现象**
`wf_org_catalog` 提供的 `rules.patchContract` 只给出 op 形状、角色节点 data 字段与错误码语义；
`rules.graphSemantics` 只给出连线的**概念**语义。但实际决定补丁能否落盘的是图检查器
（`GRAPH_INVARIANT_CODES` 24 条）与结构校验（`validate.ts` 的 `handleMismatch`/`groupMemberFlowHandle`/
`proxyParallel`/`parentUnique`/`stageLabelLocked`/`contentLabelRequired`/`mode1StartCtxOut` 等），
这些规则在工具返回的规则文本中没有清单。

**实际行为 vs 预期行为**
- 预期：按 `rules` 返回的契约即可写出一次通过的补丁。
- 实际：为写出一次通过的补丁，规划期不得不额外读取 `src/host/graph/model.ts`（连接点矩阵）、
  `invariants-types.ts`（code 注册表）、`invariants-rules-flow.ts`、`invariants-rules-nodes.ts`、
  `validate.ts` 五处源码；且即便读完，仍因规则文本与实现不一致（D-01）被整批阻断一次。

**影响**
- 规划期 token 成本显著上升（读源码 + 被阻断后重写补丁 + 重发 80 个 op）。
- 错误暴露时机滞后：阻断发生在提交后，而非规划前；规划者缺少"提交前自检清单"。
- 连带暴露的契约缺口（建议在运行阶段一并核实）：
  1. `rules.graphSemantics` 第 3 条（db 线目标必须是数据库节点）与 `HANDLE_PAIRING` 冲突（即 D-01）；
  2. 协作组成员**不得有流程线**（`groupMemberFlowHandle`）未在规则文本中提示；
  3. 主节点与其虚拟节点**不得连入同一目标的同一连接点**（`proxyParallel`）未在规则文本中提示，
     而 proxy 复用极易踩中（本次规划中被迫调整了汇合点设计）；
  4. 阶段节点 label 锁定、条件线 `content` 必须带 label 等校验项未在规则文本中提示。

**定性需求**：请用户判定这属于「工具应补充契约文档」还是「设计如此、规划者应自行读图校验器代码」。
本次按"记录证据、不擅自改文档"处理。

**编排成本观察（供运行阶段量化）**
任务书 `file` 节点（约 1.7 千字）以 ctx 线注入 17 个下游节点，即同一份长文本被静态重复注入约 2.9 万字；
这是为换取"每个节点都拿到硬约束"的刻意设计，运行阶段应实测其对上下文占用与 token 消耗的实际影响，
并与"只连首节点、其余靠文件路径传递"的方案做对照。

## D-03（P0）惰性嵌入引擎被当作已就绪读取：语义检索恒降级，经验写入永久失败

**现象（第一手）**
以 `agent` 类型提交经验时被拒：

```
语义嵌入能力不可用（当前为 BM25 词法检索）：经验入库要求语义去重，本次未写入任何内容；请确认嵌入服务可用后重试。
```

**反证（只读探针 `.tmp/probe-embedding.mjs`，纯 Node v24.17.0）**

```
source = local | dimension = 512 | 耗时 = 1936 ms
embed OK | 维度 = 512 | 模长 = 1.000000 | 耗时 = 14 ms
```

即：依赖（`@huggingface/transformers@4.2.0`，`.pnpm` 内 `onnxruntime-node@1.24.3` / `onnxruntime-web` / `sharp`
均在位）、资产（`assets/models/bge-small-zh-v1.5/onnx/model_quantized.onnx` 24MB，与 `dtype:'q8'` 匹配）、
路径推导（`lib/embedding/` 上两级到包根）三者全部正确。**故障在进程内的调用路径，不在模型本身。**

**根因链（惰性就绪态被当作就绪态读取）**
1. `src/host/embedding/engine.ts:104`：`readonly source = 'bm25'`、`readonly dimension = 0`——**初始值即降级态**；
   `engine.ts:120-124` 只有 `await ensureReady()` 才会把 `source` 置为 `'local'`。
2. `src/host/visual-workflow-host.ts:161`：装配时直接 `new EmbeddingService({...})`，**没有任何预热**
   （构造函数无法 await，装配路径也未另调 `ensureReady()`）。
3. `src/host/experience/service.ts:296`：`if (embedding.source === "bm25") throw ...`——在读取就绪态之前先判定，
   而真正会触发 `ensureReady()` 的 `embedding.embed()` 在下一行（299）才调用。**先判定、后就绪**，形成死锁：
   这条链路上永远没有机会让引擎变成 `local`。
4. 同源影响面（同一个"未就绪即读"模式）：
   - `src/host/experience/retrieval.ts:159,161`：按 `source` 判定 semantic / bm25 → 未预热时**静默退化**为词法检索，
     用户关注的"召回结果与优先级是否真实影响后续决策"因此失真；
   - `src/host/experience/service.ts:210-211,339-340`：把 `embeddingModel='bm25'`、`embeddingDimension=0`
     写入 provenance——即使写入成功，记录的嵌入来源与维度也是错的。

**影响**
经验写入路径在未预热场景下 100% 失败（对本次实验意味着"经验系统能否生成、保存"整链不可验证）；
语义检索能力实际不可用，与用户"语义检索一定要能用"的要求直接冲突。

**修复方向（先定设计层再动手；三选一或组合）**
- A. 宿主装配预热：在 `visual-workflow-host.ts` 装配处 `ensureReady()`（语义最集中，需确认装配生命周期是否 async）。
- B. 读取方先就绪：经验域在读取 `source` / `dimension` 前 `await ensureReady()`（最小改动，直击根因）。
- C. 契约改造：`ExperienceEmbeddingPort` 暴露 `ensureReady`，由经验域显式就绪（改变端口契约，须同步调用方与测试）。

**回归要求**
新增一例「惰性未预热引擎下 experience 写入成功」的测试锁定该行为——当前测试显然未覆盖此路径，否则不会漏出；
并覆盖 retrieval 在预热后确实走 semantic 分支。

**用户裁决（2026-10-10）**：定性为**缺陷**，明确要求「语义检索一定要能用」。

### 初期修复（2026-10-10 本会话完成，按用户要求未做重启验证）

同一根因（惰性就绪态被当作就绪态读取），修 5 处 + 契约层显式化：

1. `src/host/embedding/engine.ts`：`EmbeddingEngine` 接口补 `ensureReady()`——就绪本就是引擎契约的一部分
   （`EmbeddingService` 已实现，只是接口未声明）；任何读 `source`/`dimension` 做能力判定的调用方都必须先就绪。
2. `src/host/experience/ports.ts`：`ExperienceEmbeddingPort` 补 `ensureReady()`，并写明「就绪前 source 恒为 bm25
   表达的是尚未探测，而不是已降级」。
3. `src/host/experience/service.ts`：`embedOutOfTransaction` 读 source 判定前先 `await ensureReady()`
   ——这是经验写入 100% 失败的直接修复点。
4. `src/host/experience/retrieval.ts`：召回通道选择前先 `await ensureReady()`（无命中分支不触发加载，仅标注来源）。
5. `src/host/embedding/indexer.ts`：`rebuild` 与 `search` 判定 `engine.source` 前先 `await ensureReady()`
   ——否则数据库向量索引会被永久写成词法索引、检索永久退化。

**新增回归用例 3 例**（锁定「未就绪不再被误判成降级」）：
- `tests/host/experience/service.test.ts`：`test_惰性引擎就绪前的 source 为 bm25_就绪后写入成功`
- `tests/host/experience/retrieval.test.ts`：`test_惰性引擎就绪前的 source 为 bm25_就绪后走语义通道`
- `tests/host/embedding/indexer.test.ts`：`test_rebuild_引擎尚未就绪_先就绪再判定故仍写入向量索引`

测试 fixture 新增 `onEnsureReady` 就绪钩子以模拟惰性引擎；契约变更由 `pnpm typecheck` 强制暴露并已同步 9 处 fake。

**验证证据**
- `pnpm typecheck` 通过；受影响域 `381/381` 通过。
- 全量 `pnpm test`：`2586/2587` 通过——唯一失败是 `tests/host/service/manager.test.ts` 的负载型 flaky
  （断言等待文档落盘为 crashed），**单独重跑 19/19 通过**，该文件与嵌入/经验无依赖，判定与本次改动无关。
- 真实路径探针（真实惰性引擎 + 真实 `VectorIndex`，见 `probe-fix-verify.mjs`）：
  `就绪前 source=bm25/dim=0 → rebuild 后 source=embedding/dim=512/首块 512 维 → search source=embedding`
  → 「修复生效（未预热也能建立并使用向量索引）」。
- `pnpm build` 已执行，`lib/` 产物时间戳 **2026-10-10 01:21:05**：**新代码需重启 harness 后才在插件中生效**
  （本次未重启，符合用户要求）。

**修复前的三工具实测基线**（当前进程仍是旧代码；三个工具注册与调用都正常）
- `wf_experience_recall` → 正常返回 `{hits:[], kind:"candidates", source:"bm25"}`（库中确无经验，来源标注受本缺陷影响）；
- `wf_experience_learn` → 复现本缺陷：`语义嵌入能力不可用（当前为 BM25 词法检索）…`；

## D-04（P3）两条工具行为观察（正面 / 待改进各一）

1. **正面**：规划期未启动运行编排时，`wf_experience_learn` 拒绝以 `orchestrator` 类型提交，错误信息明确给出
   当前实际职责（执行主体/agent）与可选类型，可行动、无需试错——工具错误信息质量良好。
2. **待改进（可观测性）**：`engine.ts:179` 的降级警告走 `logger.warn`，但在本机可查日志中没有任何落盘
   （`.tmp/*.log`、`guardian/guardian.log` 均无匹配）。降级静默发生，使用者无法从日志定位"为什么变成 BM25"，
   只能靠主动探针复现——这在长周期无人值守场景下会显著增加排障成本。

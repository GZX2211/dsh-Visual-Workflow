## 已修复项

### D-01 P0 数据库节点无法接入连线
- **问题**：`db-out` 目标校验要求指向 database，但 database 无 `db-in`；连角色节点被拦，连自身也被连接点矩阵拦，导致 database 节点无法入图。
- **裁决**：校验器缺陷。正确语义是「数据库出线只能连到角色节点的数据库入点」。
- **修复**：修正 `ruleDbTarget`、注册表描述、`org-sop` 连线文案、相关测试；补「database → 角色节点合法」「指向非角色节点非法」用例。
- **验证**：重启后补 2 个 database + 2 条 db 线，`applied:6, ok:true`；模板 `revision=2`，27 节点 / 59 连线。
- **遗留小项**：database 之间是否需要直连未确认；当前矩阵无 `db-in`，不能自连。

### D-02 P2 写图契约未覆盖结构校验规则

- **裁决**：工具应补齐契约。
- **修复**：`org-sop` 的 `graphSemantics` 新增「连接点矩阵」「提交前自检」，覆盖 start/end/pause、agent/parent/proxy、file、database、group，以及原子失败类硬规则。
- **验证**：typecheck 通过；相关测试 414/414 通过。
- **观察**：file 节点长文本以 ctx 线注入 17 个下游，约重复 2.9 万字；运行期应实测 token/上下文成本，并与“只连首节点、靠路径传递”对照。

### D-07 P1 写图强制受管文件挡住未来交付文件

### D-09 召回路径继承写入侧职责门禁

- **验证**：typecheck、相关测试 398/398、探针通过；二次重启后终验：改过图后仍可召回 agent 经验，`source:"semantic"`，命中排序合理。

## 未修复/待裁决项

### D-06 P2 全量门禁存在负载型 flaky
**现象**  
两次全量 `pnpm test`（`--pool=threads`，全仓 219 个文件并行）各出现 1 例失败，且文件不同：
- `tests/host/service/manager.test.ts`「status：内存存活时带 pid，否则读文档」：等待文档落盘为 `crashed`，15s 超时；
- `tests/host/orchestrator/watchdog.test.ts`：等待 `runs/run-1.json` 落盘为 `stopped`，15s 超时。  
两者单独复跑分别 `19/19`、`5/5` 通过，毫秒级完成。

**性质**  
不是功能缺陷，而是**门禁可信度**问题：等待型断言（`vi.waitFor` + 真实 fsync）在满负载并行下会误报，使“改动是否引入回归”的判断失真。本轮两次都需先单跑排除，才敢确认无回归。

**建议方向（需用户裁决）**
1. 把落盘等待改为可控等待：注入 fsync 完成钩子或 fake timer，从根上消灭真实时间竞争；
2. 或把这两个用例放到串行池，与并行负载解耦；
3. 或拆分全量门禁为“并行跑其余 + 串行跑落盘等待类”，并把“全量失败先单跑该文件”固化为处置口径。

**当前处置**  
本轮取第 3 条最小形式：在 `接续说明.md` 写明处置口径，**不改测试**，避免扩大改动面。

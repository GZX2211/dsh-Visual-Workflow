## 1. 背景与目标

定时任务当前由两层语义决定是否触发：

1. **执行窗口（第一层）**：日期范围 × 有效星期 × 可执行时间段；
2. **触发策略（第二层）**：定点时刻或固定间隔，产出理论触发点。

需求是在触发策略之下增加**可开关的第三层：条件触发**。开启后，每个理论触发点到达时先运行用户选定的脚本；只有脚本返回 `true` 才真正执行任务，返回 `false` 或脚本异常则不执行。

### 1.1 已确认的产品语义

- 条件层**可开关，不是必填**；未开启时行为与升级前完全一致。
- 开启并配置脚本后，必须「执行窗口 ∧ 触发策略 ∧ 条件为 true」三者同时满足才触发。
- 脚本由用户自编写，只要求返回值是布尔值。
- 条件层只作用于**新触发点**；窗口结束挂起、窗口开始续跑、并发跳过都不运行脚本。
- 配置条件层后，实际执行时刻会比理论触发时刻晚，晚的时长取决于脚本运行时间，这是正常行为。
- 触发点到达但脚本返回 `false` 时，该触发点作废（不补打、不重试），任务不执行。

### 1.2 原始使用场景（设计必须覆盖）

用户希望定时任务在触发时检查 GitHub 上是否存在某个 Issue：

- 存在 → 条件为 `true` → 执行工作流；
- 不存在 → 条件为 `false` → 本次不执行。

检测依赖 `gh`（或 `git`）命令。Node 脚本可以完成任务：脚本内部用 `child_process` 调用 `gh issue list ...`，把结果打印为 `true` / `false`。本文 §8 给出可直接复制的模板。

### 1.3 非目标（本次不做）

- 不做「条件命令」模式（UI 填命令行、宿主直接执行）；
- 不做内置 GitHub Issue 条件类型（仓库/关键词/状态表单）；
- 不做脚本「测试运行」按钮（不新增执行端点）；
- 不做多条件组合（AND/OR）、条件参数 UI、脚本内容上传/托管；
- 不调整调度 tick 精度（保持 30 秒）；
- 不做脚本执行沙箱、权限隔离、进程树清理；
- 条件不参与窗口续跑判定。

## 2. 已确认决策

| 决策点 | 结论 | 理由 |
|---|---|---|
| 实现形态 | Node 条件脚本（`.mjs` / `.cjs` / `.js`） | 通用、符合批注；命令模式要处理 shell 分词与跨平台，内置 GitHub 条件让调度器耦合具体平台 |
| 返回值 | stdout **最后一行** 为 `true` / `false`（忽略大小写与首尾空白），且退出码为 0 | `gh --jq 'length > 0'` 天然输出布尔；允许脚本前面有日志 |
| 超时 | 固定 10 秒；超时终止并视为不通过 | 控制单任务对 tick 扫描的阻塞上限 |
| 异常语义 | 非零退出 / 超时 / 输出非法 / 无法启动 → 视为**不通过**并记录原因 | 条件层是门控，异常不应误触发任务 |
| 文件选择 | 绝对路径文本框 + 「选择文件」按钮，复用任务节点的桌面路径桥 | 浏览器不能直接取路径；桌面端桥可拿绝对路径，Web 端降级提示手填 |
| 路径范围 | 任意绝对路径 | 与「新会话工作区」同口径；本机可信模型 |
| 作用范围 | 仅新触发点 | 续跑不是新触发；避免把断点轮次挡在窗口外 |
| 结果记录 | 复用 `lastResult = 'skipped'`，原因写入 `lastError` | 用户裁决；不新增枚举，减少契约变更 |
| 模板 | 方案文档给完整模板 + 表单 hint，不自动写盘 | 不产生额外副作用与模板副本 |
| 运行上下文 | `cwd` = 脚本所在目录；继承宿主进程环境 + `WF_*` 变量 | 脚本可直接复用 `gh` 登录态与 `GH_TOKEN` |
| 客户端即时校验 | 不加条件路径校验，权威校验在 Host（保存端点 400） | 与现有「名称/模板之外字段由 Host 裁决」一致，避免双份校验漂移 |

### 3.2 关键现状

- 新触发的唯一入口是 `SchedulerEngine.fire()`；窗口挂起（`suspendByWindow`）、窗口续跑（`resumeWindowPaused`）、并发跳过（`consumeDueTrigger`）是另外的路径。
- `nextTriggerAt()` 已保证触发点落在执行窗口内；`lastConsumedTriggerAt` 防止同一触发点重复消费。
- 默认 tick 为 30 秒，触发判定发生在 tick 上。
- 任务实体新增字段必须是可选的，旧数据缺省即「未启用条件」。
- `ScheduledTaskRuntime.lastResult` 当前为 `'started' | 'resumed' | 'failed' | 'skipped' | null`，本次不新增取值。

### 3.3 唯一挂载点

```
runTaskOnce（idle 分支）
  └─ nextTriggerAt 到期
       └─ gateAndFire(task, rt, triggerAt)     ← 本次新增
            ├─ 条件未启用 → fire()（现有逻辑）
            └─ 条件启用   → 运行脚本
                 ├─ true  → fire()
                 └─ false/异常 → 消费触发点、记录 skipped + lastError、return
```

窗口挂起、窗口续跑、并发跳过三条路径**不经过** `gateAndFire`。

## 4. 数据契约

### 4.1 共享类型（`src/host/shared/scheduler-types.ts`）

新增：

```ts
/**
 * 第三层：条件触发配置（可选；未配置 = 未启用）。
 * 开启后每个新触发点先运行脚本，仅当脚本返回 true 才执行任务。
 */
export interface ScheduleConditionConfig {
  /** 是否启用条件层。 */
  enabled: boolean
  /**
   * 条件脚本绝对路径（.mjs/.cjs/.js）。
   * 关闭条件层时保留原值，便于重新开启；运行期不读取。
   */
  scriptPath: string
}
```

`ScheduledTask` 增加可选字段：

```ts
/** 第三层：条件触发（可选；缺省 = 未启用，旧数据兼容）。 */
condition?: ScheduleConditionConfig | null
```

同时把 `ScheduleConditionConfig` 加入 `src/host/shared/types.ts` 的 scheduler type-only re-export 块（保持既有契约路径 `from './types.js'` 可用）。

不修改 `ScheduledTaskRuntime`（结果复用 `skipped`）。

### 4.2 请求解析（`parseScheduledTaskInput`）

规则：

- `input.condition` 不是对象 → `null`；
- 是对象 → `{ enabled: input.condition.enabled === true, scriptPath: String(input.condition.scriptPath ?? '').trim() }`；
- 不因形状非法抛错（与现有字段一致，业务规则交给 `validateScheduledTask`）。

### 4.3 校验（`validateScheduledTask`，同步纯函数）

仅当 `condition.enabled === true` 时校验（判定函数来自 §5.1 的纯规则模块）：

1. `scriptPath` 非空，否则返回「启用条件触发时请选择脚本文件」；
2. `isAbsoluteConditionScriptPath(scriptPath)` 为真，否则返回「条件脚本路径必须是绝对路径」；
3. `hasSupportedScriptExtension(scriptPath)` 为真，否则返回「条件脚本仅支持 .mjs/.cjs/.js 文件」。

关闭条件层时**不校验**路径（允许保留历史值）。

> 文件存在性属于 IO，放在保存端点（§4.6），不在同步校验里做。

### 4.4 规范化（`normalizeScheduledTask`）

```ts
const rawCondition = task.condition
const condition = rawCondition
  ? { enabled: rawCondition.enabled === true, scriptPath: String(rawCondition.scriptPath ?? '').trim() }
  : null
```

化简规则（保持存储干净、同时不丢用户输入）：

- 原始 `condition` 缺失 → `null`；
- `enabled === false` 且 `scriptPath === ''` → `null`；
- `enabled === false` 且路径非空 → 保留 `{ enabled: false, scriptPath }`（重新开启不必重填）；
- `enabled === true` → 保留（此时路径已由校验保证非空）。

### 4.5 旧数据兼容

- 旧任务没有 `condition` 字段 → `parse` 得到 `null`，引擎不评估条件，行为与升级前完全一致。
- `schedulerTaskPut` 是**整任务替换**语义：请求体不带 `condition` 时，保存结果会把条件配置清空（与现有 `workspacePath` 一致）。外部调用方必须回传完整任务；文档与测试中显式记录这一点，本次不为此引入「缺省保留旧值」的特殊合并逻辑。
- UI 读取 `draft.condition?.enabled === true`，旧任务打开时条件层显示为关闭。

### 4.6 保存端点校验（`src/host/api/scheduler.ts`）

在现有 `workspacePath` 校验之后，对启用条件层的任务追加：

```ts
if (task.condition?.enabled === true) {
  await validateConditionScriptPath(task.condition.scriptPath)
}
```

`validateConditionScriptPath` 由 scheduler 模块提供（§5.3），失败抛面向用户的中文错误，端点转 400：

- 不存在 / 不可访问：`条件脚本文件不存在或不可访问：<原路径>（请填写存在的绝对路径文件）`
- 不是普通文件：`条件脚本路径不是文件：<原路径>`

关闭条件层时不读盘。

## 5. 条件脚本执行器

### 5.1 模块划分

按「纯规则 / IO」拆成两个文件，避免配置子域依赖执行器：

**`src/host/scheduler/condition-config.ts`（纯函数，零 IO）**

- `isAbsoluteConditionScriptPath(path: string): boolean`（基于 `node:path.isAbsolute`）；
- `hasSupportedScriptExtension(path: string): boolean`（`.mjs` / `.cjs` / `.js`，大小写不敏感）；
- `parseConditionOutput(lastLine: string): { pass: boolean; detail: string }`（对 stdout 最后一行的判定）。

`task-config.ts` 只依赖本文件，不引入任何 IO。

**`src/host/scheduler/condition-script.ts`（IO）**

- `validateConditionScriptPath(raw: string): Promise<void>`（保存时 `stat`）；
- `createConditionScriptRunner(options?): ConditionScriptRunner`（`spawn`、超时、输出采集，内部复用 `parseConditionOutput`）；
- `ConditionScriptInput` / `ConditionScriptOutcome` / `ConditionScriptRunner` 类型。

引擎不直接使用 `child_process` 或 `fs`，只通过依赖缝调用执行器；测试可注入 fake。

### 5.2 类型与依赖缝

```ts
/** 条件脚本执行输入（引擎提供，脚本可经环境变量读取）。 */
export interface ConditionScriptInput {
  scriptPath: string
  taskId: string
  taskName: string
  templateId: string
  /** 理论触发时刻（UTC 毫秒）。 */
  triggerAt: number
  timezone: string
  ownerSessionId: string
}

/** 条件脚本执行结果；pass=false 时 detail 为可展示的原因。 */
export interface ConditionScriptOutcome {
  pass: boolean
  detail: string
}

/** 执行器缝（引擎只依赖此接口）。 */
export interface ConditionScriptRunner {
  run(input: ConditionScriptInput): Promise<ConditionScriptOutcome>
}
```

工厂：

```ts
export interface ConditionScriptRunnerOptions {
  /** 测试注入；缺省使用 node:child_process.spawn。 */
  spawnImpl?: typeof spawn
  /** 测试注入；缺省 process.execPath。 */
  execPath?: string
  /** 超时毫秒（缺省 10_000）。 */
  timeoutMs?: number
  /** 测试注入；缺省 process.env。 */
  env?: NodeJS.ProcessEnv
  /** 测试注入；缺省 Boolean(process.versions.electron)。 */
  isElectron?: boolean
}

export function createConditionScriptRunner(options?: ConditionScriptRunnerOptions): ConditionScriptRunner
```

### 5.3 保存时路径校验

```ts
export async function validateConditionScriptPath(raw: string): Promise<void>
```

- 入参已是 Host 校验过的绝对路径；仍按原样 `stat`；
- `ENOENT` / `EACCES` / `ENOTDIR` / `EPERM` → 抛「不存在或不可访问」；
- `!info.isFile()` → 抛「不是文件」；
- 其它错误原样抛出（端点按内部错误处理）。

### 5.4 运行方式

```ts
const isElectron = options.isElectron ?? Boolean(process.versions.electron)
const child = spawn(execPath, [scriptPath], {
  cwd: dirname(scriptPath),
  env: {
    ...env,
    // Electron 打包的宿主进程：让 electron 二进制以 Node 模式运行脚本。
    ...(isElectron ? { ELECTRON_RUN_AS_NODE: '1' } : {}),
    WF_TASK_ID: input.taskId,
    WF_TASK_NAME: input.taskName,
    WF_TEMPLATE_ID: input.templateId,
    WF_TRIGGER_AT: new Date(input.triggerAt).toISOString(),
    WF_TIMEZONE: input.timezone,
    WF_SESSION_ID: input.ownerSessionId,
  },
  stdio: ['ignore', 'pipe', 'pipe'],
  windowsHide: true,
})
```

说明：

- **不经过 shell**：避免引号/转义与平台分派问题；脚本内部自行调用 `gh`、`git`。
- **Electron**：DSH 桌面端宿主运行在 Electron 进程中，`process.execPath` 是 electron 可执行文件；`ELECTRON_RUN_AS_NODE=1` 使其按 Node 运行脚本。纯 Node 环境（headless/service）不加该变量。
- **cwd** 固定为脚本所在目录，相对路径依赖（如脚本同目录的配置文件）可预期。
- **env** 继承宿主进程环境（含 `PATH`、`GH_TOKEN` 等），再覆盖 `WF_*`。
- **stdin** 关闭，避免脚本等待输入。

### 5.5 判定规则

执行器维护：

- stdout 的最后一行（trim，最多保留 1 KB，避免内存膨胀）；
- stderr 的尾部摘要（最多保留 2 KB，用于 `detail`）；
- 超时计时器（10 秒）；
- `error` 事件（spawn 失败）。

结果判定顺序：

| 情况 | 结果 |
|---|---|
| 超时（计时器触发后 kill） | `{ pass: false, detail: '条件脚本执行超时（10 秒）' }` |
| spawn 报错（如 ENOENT） | `{ pass: false, detail: '无法启动条件脚本：<message>' }` |
| 退出码非 0 | `{ pass: false, detail: '条件脚本退出码 <N>：<stderr 尾部摘要>' }` |
| 退出码 0 且最后一行（小写）为 `true` | `{ pass: true, detail: '' }` |
| 退出码 0 且最后一行（小写）为 `false` | `{ pass: false, detail: '条件脚本返回 false' }` |
| 退出码 0 但输出为空/其它 | `{ pass: false, detail: '条件脚本输出不是 true/false：<最后一行摘要>' }` |

实现要点：

- 只在 `close` 事件后 resolve（保证输出收集完整）；
- 超时 kill 后加 1 秒兜底计时器，若仍未 `close` 也 resolve 超时结果，避免执行器永久挂起；
- kill 使用 `child.kill('SIGKILL')`（Windows 下为强制终止）；
- 计时器与兜底计时器在 resolve 前清理。

### 5.6 引擎侧评估

`SchedulerEngineDeps` 增加可选缝：

```ts
/** 条件脚本执行器（宿主装配；测试 fake）。未装配且任务启用条件时按不通过处理。 */
conditionRunner?: ConditionScriptRunner
```

引擎私有方法：

```ts
private async evaluateCondition(task: ScheduledTask, triggerAt: number): Promise<ConditionScriptOutcome> {
  if (task.condition?.enabled !== true) return { pass: true, detail: '' }
  if (!task.condition.scriptPath.trim()) return { pass: false, detail: '条件脚本路径为空' }
  const runner = this.deps.conditionRunner
  if (!runner) return { pass: false, detail: '条件脚本执行器未装配' }
  try {
    return await runner.run({
      scriptPath: task.condition.scriptPath,
      taskId: task.taskId,
      taskName: task.name,
      templateId: task.workflowTemplateId,
      triggerAt,
      timezone: task.timezone,
      ownerSessionId: task.ownerSessionId,
    })
  } catch (error) {
    return { pass: false, detail: `条件脚本执行失败：${String(error instanceof Error ? error.message : error)}` }
  }
}
```

> 引擎属 scheduler 模块，只依赖 shared 与模块内部，不引入 orchestrator 的 `messageOf`。
> 实现时先用局部变量收窄 `const condition = task.condition`，避免可选链判断后 TypeScript 仍未收窄。

### 5.7 已知限制（显式记录）

- 超时只 kill 直接子进程；脚本内部再起的 `gh` 子进程可能残留（不做进程树清理）。
- 引擎 `dispose()` 不取消在途脚本；最长 10 秒后自然结束。
- 脚本以宿主进程权限运行，可读写本机文件、访问网络、读取继承的环境变量；**不做沙箱**。
- 脚本输出只在内存中保留尾部，超长输出会被截断（不影响最后一行判定）。

## 6. 引擎状态机改动

### 6.1 触发流程

`runTaskOnce` 的 idle 分支保持触发点判定不变，把 `fire` 调用改为 `gateAndFire`：

```ts
const nextT = nextTriggerAt(task, rt.lastConsumedTriggerAt ?? this.startedAtMs, task.timezone)
if (nextT === null || nextT > now) return
await this.gateAndFire(task, rt, nextT)
```

新增：

```ts
private async gateAndFire(task: ScheduledTask, rt: PersistedRuntime, triggerAt: number): Promise<void> {
  if (task.condition?.enabled === true) {
    const outcome = await this.evaluateCondition(task, triggerAt)
    if (!outcome.pass) {
      // 触发点作废：推进游标、记录跳过原因，不补打、不重试
      rt.lastConsumedTriggerAt = triggerAt
      rt.lastResult = 'skipped'
      rt.lastTriggeredAt = new Date(triggerAt).toISOString()
      rt.lastError = outcome.detail
      await this.persist(task.taskId, rt)
      this.deps.logger?.info?.(
        `[visual-workflow] 定时任务 ${task.taskId} 条件未通过，跳过本轮：${outcome.detail}`,
      )
      return
    }
  }

  // 条件未启用或通过：走现有触发路径（内部消费触发点并落盘）
  await this.fire(task, rt, triggerAt)
}
```

- `fire()` 内部现有的 `rt.lastConsumedTriggerAt = triggerAt` 保留；条件通过时不重复设置。
- 条件通过 → 走现有 `fire`，`lastResult='started'`、`lastError=''`，与升级前一致。
- 条件不通过 → `lastResult='skipped'`，`lastError` 写原因；`currentRunId` 保持 `null`，`deriveStatus` 得到 `idle`（不是 `error`）。
- 条件评估抛错不会向上冒泡（`evaluateCondition` 内部收敛为不通过），不影响同批其它任务。

**为什么评估期间不会重复评估同一触发点**：`sweep()` 已有在途去重（重叠 tick 共享同一次扫描）；
进程在评估期间崩溃时，重启后的 `missedTrigger=skip` 会把启动基准推进到引擎启动时刻，
同一触发点不会被补评估。因此 `gateAndFire` 只在最终决策时消费游标，正常路径只写一次盘。

### 6.2 各路径与条件层的关系

| 场景 | 是否运行条件脚本 | 结果 |
|---|---|---|
| 新触发点到期（idle） | 是 | 通过 → 执行；不通过 → `skipped` + `lastError` |
| 执行中窗口结束（挂起） | 否 | 现有挂起逻辑 |
| 窗口暂停后进入下一窗口（续跑） | 否 | 现有续跑逻辑 |
| 执行中又到触发点（并发跳过） | 否 | 现有 `consumeDueTrigger('skipped')` |
| 任务停用 | 否 | 现有逻辑 |
| 用户接管 / run 终态 | 否 | 现有清空逻辑 |

### 6.3 时序细节

- **条件评估期间窗口结束**：仍执行任务。触发点在评估开始时已成立；脚本耗时不应反悔，否则会因几秒网络延迟丢掉一轮。
- **条件评估期间任务被停用/删除**：当前轮次继续（与现有「删除只影响未来触发」一致）；下一 tick 才按新配置决策。删除任务与写回运行时存在既有竞态，本次不新增处理。
- **配置修改**：`configUpdate=immediate` 语义不变，保存后的下一 tick 生效；正在运行的脚本使用本轮开始时的任务快照。
- **时间记录**：`lastTriggeredAt` 记录理论触发时刻（与现有语义一致），不是实际执行时刻；实际延迟 = tick 等待（≤30 秒）+ 脚本耗时（≤10 秒）。

### 6.4 日志

| 事件 | 级别 | 文案要点 |
|---|---|---|
| 条件通过 | 不额外打日志（沿用触发日志） | — |
| 条件不通过（含脚本 false / 异常 / 超时） | `info` | 任务 id + 原因（原因同时写入 `lastError`） |

> 条件层是正常门控，`false` 与脚本异常都不升级为 `warn`；可排查信息统一放在运行态 `lastError`，避免周期性任务刷告警日志。

## 8. 脚本编写规范与模板

### 8.1 契约（写给脚本作者）

1. 运行时：Node（`.mjs` / `.cjs` / `.js`），由 DSH 宿主用其自带的 Node 可执行文件启动。
2. 工作目录：脚本所在目录。
3. 环境变量：继承宿主进程环境；额外提供：
   - `WF_TASK_ID` 任务 id
   - `WF_TASK_NAME` 任务名称
   - `WF_TEMPLATE_ID` 工作流模板 id
   - `WF_TRIGGER_AT` 理论触发时刻（ISO 8601，UTC）
   - `WF_TIMEZONE` 任务时区
   - `WF_SESSION_ID` 任务归属会话 id
4. 返回值：
   - stdout **最后一行** 必须是 `true` 或 `false`（大小写不敏感，允许前后空白）；
   - 允许在它之前输出日志（日志建议写 stderr）；
   - 退出码必须为 0。
5. 失败语义：退出码非 0、10 秒超时、没有输出或输出不是布尔 → 条件不通过，任务本轮不执行，原因显示在运行态摘要的 `lastError`。
6. 条件为 `true` 才执行任务；如果希望「不存在某物时才执行」，请让脚本输出取反。

### 8.2 GitHub Issue 检测模板（可直接复制）

保存为 `.mjs` 文件（例如 `D:\scripts\check-issue.mjs`）：

```js
// 条件脚本：GitHub 上存在匹配 Issue 时输出 true，否则输出 false。
// 契约：stdout 最后一行必须是 true/false，退出码 0。
// 如果宿主 PATH 找不到 gh，请把 GH 改成 gh.exe 的绝对路径。
import { execFileSync } from 'node:child_process'

const GH = process.env.GH_BIN || 'gh'
const REPO = 'owner/repo'          // 改成你的仓库
const SEARCH = '关键字 in:title'   // GitHub 搜索语法；可加 label:xxx
const STATE = 'open'               // open / closed / all

try {
  const out = execFileSync(GH, [
    'issue', 'list',
    '--repo', REPO,
    '--search', SEARCH,
    '--state', STATE,
    '--json', 'number',
    '--limit', '1',
    '--jq', 'length > 0',
  ], { encoding: 'utf8', stdio: ['ignore', 'pipe', 'inherit'] }).trim()

  // --jq 输出就是 true/false；保险起见再归一化一次
  console.log(out === 'true' ? 'true' : 'false')
} catch (error) {
  // 无法判定（未登录、网络失败、gh 不存在）：非零退出 → 条件不通过并记录原因
  console.error(`gh 执行失败：${error instanceof Error ? error.message : String(error)}`)
  process.exit(1)
}
```

验证方法（先在终端确认脚本本身可用）：

```powershell
node D:\scripts\check-issue.mjs
# 期望输出：true 或 false
echo $LASTEXITCODE
# 期望：0
```

### 8.4 常见问题

- **找不到 `gh`**：GUI 启动的进程 PATH 可能与终端不同；用绝对路径或设置 `GH_BIN`。
- **私有仓库**：确保 `gh auth status` 在宿主用户下可用，或设置 `GH_TOKEN`。
- **限流**：条件脚本每个触发点运行一次；高频任务请自行加缓存或降低触发频率。
- **误触发**：脚本异常被当作不通过；如果希望网络异常时仍执行，请在脚本内捕获并输出 `true`（自行承担风险）。

## 9. 安全边界（必须在文档与发布说明中声明）

- 定时任务是**全局共享**资源（跨会话可见、任意会话可创建/编辑），这是既有设计（K1）。
- 条件脚本以**宿主进程权限**执行，等价于用户在本机运行任意代码：可读写文件、访问网络、读取继承的环境变量（可能包含 API Key）。
- 允许任意绝对路径，没有脚本目录白名单，也没有沙箱。
- 结论：只应配置可信脚本；任何能访问本机 GUI API 的调用方都能借此执行代码。若未来收紧，可增加「限定 dataDir/scripts」或脚本白名单，但本次明确不做。

## 14. 附：需求批注原文要点

> 在触发策略之下，再增加一个条件触发（第三层）；该层功能可开关，不是必填。
> 1. 该层功能未开启时，就是常规的定时任务，和此前逻辑无区别。
> 2. 当该层开启且配置了条件时，必须 3 层同时满足才能触发，且条件返回必须为 true。
>
> 条件层使用方法：
> 1. 条件层 UI 配置一个脚本文件选择器，点击选择按钮后，将该脚本填入。脚本可自编写，只需保证其返回值必须是布尔值（true 和 false）。
> 2. 当前两层的时间触发时，运行该脚本，待读取脚本返回值为 true 后，开始执行定时任务。
> 3. 配置条件层后，实际触发时刻会比原本定义时刻晚几秒，取决于脚本运行时间，这是正常行为。
> 4. 如果时刻到达了，但脚本运行返回为 false，那么该定时任务将不会执行。
>
> 可能需要规定脚本的编写方式和给定模板，看如何实现。

本方案对批注的落地差异（均为已确认裁决）：

1. 「脚本文件选择器」在 Web 环境无法取得绝对路径，因此实现为「文本框 + 复用桌面选择文件按钮」，Web 端降级为手填；
2. 「晚几秒」实际还包含 tick 等待（≤30 秒），条件脚本只额外增加执行时间（≤10 秒）；
3. 脚本异常/超时按「不通过」处理，而不是误触发；
4. 结果复用 `skipped`，原因写入 `lastError`。

### 15.2 复核发现的问题（需修正）

**F1-1（必改）：`validateScheduledTask` 的入参是字段白名单 `Pick<…>`，不含 `condition`，方案未要求扩展。**

- 依据：`task-config.ts` 第 78–81 行签名是 `Pick<ScheduledTask, 'name' | 'workflowTemplateId' | … | 'intervalConfig'>`。在该签名下，函数体内访问 `task.condition` 无法通过类型检查，实现者只能用 `as` 逃逸——这正是仓库要避免的类型逃逸。
- 可执行修正：把 `'condition'` 加入该 `Pick` 列表（调用方 `api/scheduler.ts` 与既有测试传的都是完整 `ScheduledTask`，无需改调用处），并在 JSDoc 补一句「条件层仅在 enabled 时校验路径」。

**F1-2（必改）：`parseScheduledTaskInput` 用 `...input as ScheduledTask` 展开，收敛后的 `condition` 必须写在展开之后。**

- 依据：`task-config.ts` 第 38–40 行 `return { ...(input as ScheduledTask), taskId, … }`。若把 `condition` 写在展开之前，原始请求体的未收敛值会**覆盖**收敛结果（对象字面量后者优先）。方案 §4.2 只给了规则，没提这个实现陷阱。
- 可执行修正：在返回对象中把 `condition` 放在展开之后显式赋值：
  ```ts
  condition: input.condition && typeof input.condition === 'object'
    ? { enabled: input.condition.enabled === true, scriptPath: String(input.condition.scriptPath ?? '').trim() }
    : null,
  ```
  注意 `ScheduledTask.condition` 是可选字段，解析结果统一给 `null`（不是 `undefined`），否则「整任务替换」语义下旧值清除会依赖 JSON 序列化细节。

**F1-3（必改）：`normalizeScheduledTask` 同样以 `...task` 展开，`condition` 的化简必须显式覆盖。**

- 依据：`task-config.ts` 第 130–167 行 `const normalized: ScheduledTask = { ...task, … }`。不显式赋值时 `{ enabled: false, scriptPath: '' }` 会原样落盘，方案 §4.4 要求的「关闭且空路径 → null」不会生效。
- 可执行修正：在 `normalized` 字面量里显式给出 `condition`，按 §4.4 的四条化简规则实现；`sessionMode !== 'new-session'` 时**不要**顺手删 `condition`（条件层与 sessionMode 无关）。

**F1-4（必改）：`isAbsoluteConditionScriptPath` 的跨平台语义必须在契约里写死，否则测试会假红。**

- 依据：方案 §5.1 说「基于 `node:path.isAbsolute`」，而 §11.1 又要求「Windows 盘符、UNC、POSIX 根路径为 true」。在非 Windows 平台（CI/服务端）`path.isAbsolute('D:\\a.mjs')` 返回 `false`，两条要求互相矛盾——按 §11.1 写死 Windows 期望会让 Linux 上的测试假红，按 §5.1 写又会漏掉 Windows 形态。
- 可执行修正：**以运行平台语义为准**（`path.isAbsolute`），契约 T1-1 只断言「当前平台的绝对路径为 true、相对路径/纯文件名为 false、空串为 false」；Windows 形态（盘符/UNC）的断言用 `process.platform === 'win32'` 条件包裹。理由：脚本在本机执行，路径也只在本机有意义，跨平台接受异机路径没有价值。

**F1-5（必改）：执行器必须有「resolve 后忽略迟到事件」的保护，方案 §5.5 只写了兜底计时器。**

- 依据：§5.5 要求「超时 kill 后加 1 秒兜底，若仍未 close 也 resolve」。kill 之后子进程仍可能 `emit('error')`（例如 EPERM）或 `close`。若在 resolve 之后再次 resolve 属无害，但**未监听 `error` 事件**会让 Node 抛未捕获异常，直接打崩宿主进程（定时任务在宿主进程内跑）。
- 可执行修正：执行器内部至少维护 `settled` 标志，`resolve` 后忽略后续 `error`/`close`/超时事件；`error` 监听必须常驻（不能在 `close` 后移除）。

**F1-6（补强）：`parseConditionOutput` 的职责边界要写死，避免实现者把退出码塞进纯函数。**

- 依据：§5.1 只说「对 stdout 最后一行的判定」，§5.5 的判定表又包含退出码/spawn 错误/超时，两者容易被实现成同一个函数，导致 `condition-config.ts` 出现 IO 概念（退出码来自子进程），破坏「纯规则零 IO」的模块划分。
- 可执行修正：`parseConditionOutput(lastLine: string)` 只接收文本、只判定 `true/false/其它`；退出码、超时、spawn 错误全部由 `condition-script.ts` 判定并在其 detail 中拼装。

**F1-7（补强）：宿主装配缺一条可验收条款。**

- 依据：`conditionRunner` 是可选依赖缝，未装配时引擎按「不通过」处理（§5.6）。若 `visual-workflow-host.ts` 忘记装配，功能在生产环境**恒不通过且不报错**（只在运行态 `lastError` 显示「执行器未装配」），属于典型的静默失效。
- 可执行修正：契约 T1-26 增加静态装配断言（宿主装配文件必须引用 `createConditionScriptRunner`）并写入 §12 验收。

### 15.3 未采纳的质疑（记录以免重复讨论）

- 「条件脚本改为 `execFile` 直接执行命令」：方案 §1.3 已列为非目标；`execFile` 无法覆盖 Windows 上 `.mjs` 的启动方式（需 node 解释器），且无法复用 `ELECTRON_RUN_AS_NODE`。
- 「超时用 `AbortSignal.timeout` + `execFile`」：同样受 Electron 解释器问题限制，且仓库当前没有该用法先例，不采纳。
- 「条件不通过时 `lastResult` 新增 `'condition-failed'`」：会改 `ScheduledTaskRuntime['lastResult']` 取值域（共享契约），与方案「复用 skipped」的裁决冲突，不采纳。
- 「把文件存在性校验塞进 `validateScheduledTask`」：会破坏「纯函数零 IO」的分层，不采纳（方案 §4.3 的裁决正确）。

## 17. 人工验收补充（测试不可覆盖部分）

在 §11.3 五条之外补测：

1. 开启条件但脚本路径指向目录 → 保存被拒，提示含「不是文件」，草稿内容不丢。

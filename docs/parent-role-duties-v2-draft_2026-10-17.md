## 二、五维正文草稿（待定案后落入 `texts/`）

> 收录判据（用户第 14 点）：**只写对「整个编排任务的执行」都有影响、且不随 run 组装变化的职责规范**。
> 第 10/11/12 点（`wait_agent` 等待、Team 自治域交接、Team 空组与成员安排）**不进本文**，留在外部编排
> 提示词（`texts/parent-*.ts`）；图结构硬规则与写图契约仍走按需召回（Catalog 规则段）。

```text
# 角色定位

你是本工作流的编排父代理：规划并治理这张流程图，调度子代理完成节点任务，必要时亲自执行节点任务。
你是整个流程中唯一拥有「改图」与「组织治理」权限的角色。

# 职责范围

1. 组织与改图治理：规划期建立流程结构，运行期按实际情况渐进调整；你决定「谁来做、做什么、什么时候做」。
2. 节点启动前的判断与调整：每次启动节点前完成三项判断（见「行为规范·启动前三问」），任一不满足先调整再启动。
3. 任务分配与发布：任务在节点启动时按任务规范准备并发布；图上已有任务时先核对，符合则不重复发布。
4. 结算后的履职核验与纠正：每个节点结算后核验其是否履职、是否越界、交付是否达标，必要时经消息通道纠正。
5. 阻塞识别与升级：把「代理自身无法解决、必须依赖外界环境或用户操作」的问题识别为阻塞，及时停下并等待人类决策。
6. 未解决问题闭环：子代理上报的待决策问题与未解决问题，都必须在本次运行内得到处理，不得堆积到后续流程。

# 行为规范

## 一、组织与改图

1. 角色优先级：优先复用已有角色资产；已有资产无法满足需求时，在其基础上改造；最后才新建角色（新职责）。
2. 渐进式改图：只在「下一个节点即将执行」时判断与调整，且只调整这一步——可插入修复/补充节点或条件分支，
   不改动更远的下游；随流程推进逐段重新判断，不要一次判断就改完后续全部。
3. 调整就近优先：调整时先考虑改近邻节点，其次才考虑改更远的节点。
4. 语义条件分支优先：下一个节点不符合当前任务条件时，先建立条件分支，并说明各分支分别在什么情况下适用；
   只有当「什么情况走哪条分支」无法回答时，才直接改写该节点。
5. 能汇聚不分叉：若节点已被条件化，而原本的后续节点仍符合执行条件，应让分支重新汇聚，而不是无限树状分叉。
6. 改图必须满足图结构硬规则：动手前按召回的图语义与写图契约自查，命中硬规则会让整批补丁失败。
7. Team 只在需要多成员协作或对抗式审查时规划（普通并行任务用普通节点）；团队是自治域，不自动承接上游产出、
   也不自动向下游交接，由你按阶段汇总与交接。

## 二、启动前三问（任一为「否」都要先调整，再启动）

1. 该节点能不能完成这次任务（任务粒度是否合适）？
2. 该节点适不适合这次任务（职责是否匹配）？
3. 若本次不改图，后续流程能不能正常推进（流程是否无阻塞）？

## 三、结算核验（每个节点完成汇报后）

1. 是否正确履行了职责？
2. 是否越界（做了不属于它范围的事）？
3. 是否做了超越其权限的事？
4. 交付内容是否符合分配给它的任务与输出契约？

以上任一不满足，经消息通道向该节点（或相关节点）发出纠正或补充要求；不得放着不管继续推进。

## 四、任务分配与发布

1. 规划期只规划「职责与流程」的分配，不发布任务；准确任务在节点启动时按需准备并发布。
2. 判断依据：图上已经存在用户定义的准确任务（数据节点文本连接到该节点）且适配当前角色与实际执行情况 →
   不重新定义、不重复发布，直接启动节点；图上没有清晰准确的任务，或已有任务与实际不符 → 由你发布任务
   （不符时先纠正，再发布）。
3. 任务通常很短：大部分交接信息已由上游产出与交接契约承载。任务的作用是**约束本次执行的行为范围**——
   例如上游产出 A、B、C、D 四个文件而本节点只需要 A、B，按契约全读会引入无关内容（上游的部分产出是
   为后续节点准备的）。你不需要知道交接文件的正文，只需要知道上下游各自「需要什么、产出什么」；
   只有在进入并行节点、需要任务拆解时，才必须掌握任务全貌。
4. 任务生成规范（发布任务时）：包含准确的执行路径、交付内容、执行方式与验收标准；符合所分配角色的职责范围；
   自包含、可独立执行；不与角色职责重复或冲突。
5. 任务与跨节点协调信息一律经消息通道投递（wf_send_message），不得用普通文本模拟对话或绕过工具传递。

## 五、例外与重跑

1. 流程不是不可逆的，节点也不是不可重跑的：出现例外情况或新任务时，可以重新调度已完成的节点来应对
   （新任务经消息通道下发）。

## 六、阻塞处理

1. 阻塞 = 代理自身无法解决、必须依赖外界环境或用户操作的问题；代理自身能解决的问题不叫阻塞。
2. 出现阻塞：停止继续推进后续流程，并在当前流程位置**放置一道暂停门**（用改图工具插入暂停阶段节点，
   保持流程线合法），推进到该节点即进入暂停；随后向用户说明阻塞事项与具备指导性的操作说明。
3. 部分阻塞：先把不受影响的任务执行完，直到确实无法继续时才放置暂停门。
4. 只要工作流尚未完成或失败，一律用「暂停」而非「终止」——暂停表示需要人类决策或外部环境执行后才能继续。

# 决策权限

1. 可自行决定：流程内调度、任务分配、条件分支、对子代理的纠正、渐进式改图。
2. 不可自行决定（必须上报用户）：与用户明确要求或方案冲突的决策、重大架构调整类问题、会造成不可逆影响的
   决策（例如删除数据）。
3. 子代理无法决策时上报给你，你应立即响应并在自身权限内裁决；只有超出你的权限时才上报用户（决策链顶端）。
4. 除上述约束外，严格遵守项目规范中定义的其他约束。

# 交接契约

1. 与子代理：任务内容、纠正与补充要求、决策答复——经消息通道投递，内容自包含。
2. 与用户：阻塞事项 + 具备指导性的操作说明；需要用户决策的问题。
3. 与 Team 节点：按项目阶段汇总后发布任务；在其下一节点启动时，把团队的产出交接给下游并安排任务。
4. 收尾沉淀：本次运行结束后，把可复用的编排经验沉淀给经验库（只写职责级要求，不写工具调用流程）。
```

## 六、第三轮分析：模板 / 资产 / 实例三层与召回限制（2026-10-17 用户补充口径）

用户的补充明确了三条架构约束：**模板=草稿（不叠加版本）**、**资产=迭代版本（叠加+回滚，仅作迭代管理）**、
**实例=执行权威（提示词由实例决定）**；并新增一条硬约束：**父代理提示词不得被 catalog 召回**；
以及一条权限约束：**父代理不得经 PATCH 编排自己（含插入/删除/修改父代理节点与连线）**。

### 6.1 与现状一致、无需改动的部分

| 约束 | 现状 | 结论 |
|---|---|---|
| 模板页改动不叠加版本 | `RoleTemplate` 存 FlowStore（JSON），`saveTemplate` 只覆盖模板本身 | ✅ 已满足 |
| 入库把当前提示词录成资产版本 | `promoteRole`（模板 → 角色资产 V1；内容重复报 `ERR_ASSET_DUPLICATE`） | ✅ 已满足 |
| 资产页改动叠加版本、可回滚 | `saveRoleAsset` 追加版本；`rollbackRoleAsset` 只移动 Active 指针 | ✅ 已满足 |
| 入库后在活跃资产列表置顶 | `listRoleAssets` 按 `ORDER BY a.updated_at DESC, a.asset_id ASC`（[role-assets.ts:405](../src/host/assets/role-assets.ts#L405)） | ✅ 已满足 |
| 执行提示词由实例决定 | 节点 `data.systemPrompt` 是权威；模板转实例 / 资产转实例都写进节点，运行期读节点 | ✅ 已满足 |
| 父代理图唯一性 | 图校验「parent 节点最多 1 个」 | ✅ 已满足 |

⇒ **三层架构不需要重构**，第 2 批只剩「正文来源统一 + 召回限制 + 唯一性」三类收口。

### 6.2 冲突点与影响

#### D1｜内置父代理模板的正文仍是 client 硬编码

- 现状：`src/client/i18n.ts` 的 `builtinParentPrompt`（中英各一句）由 `useStudioBoot` 播种成
  `role-parent-builtin` 模板；正文在 client 侧，且与第 1 批落库的五维正文（host `texts/`）形成两份。
- 影响：用户新建父代理实例拿到的是旧一句话；改一处另一处不跟。
- 处置：**内置父代理模板改由宿主播种**（正文 = `texts/parent-role-duties.ts` 唯一源），client 删除播种逻辑。
  播种条件沿用「模板库中没有 kind='parent' 的角色模板」。

#### D2｜父代理提示词对 catalog 全面可见（违反「不得召回」）

- 现状：`wf_org_catalog` 的索引把 `listRoleAssets()` 全量作为 `assets.roles`（[tool.ts:121-136](../src/host/tools/wf-org-catalog/tool.ts#L121)）；
  详情召回 `role-*`、`flow-*#<nodeId>`、`instance#<nodeId>` 都不区分节点 kind（父代理节点均可召回）。
- 影响：父代理会召回自己的职责提示词（无意义），且把「父代理提示词」暴露成可参考的编排资产（与其定位冲突）。
- 处置：三处来源统一禁止召回 kind='parent'：
  1. 索引：`assets.roles` 过滤 `kind === 'parent'`；
  2. 角色资产详情：目标资产 kind='parent' → 该 id 记错误（`WF_BAD_ARGS` + 可行动说明）；
  3. 内联角色（工作流资产 / 运行实例）：节点 kind='parent' → 同样拒绝。

#### D3｜父代理节点会被登记成工作流内联角色资产（破坏「唯一 + 单一版本链」）

- 现状：`insertWorkflowVersion` 对 `isRoleNode(node)` 的节点（含 parent）一律走 `registerRoleNode`，
  为父代理节点登记 inline 角色资产（[workflow-assets.ts:488-500](../src/host/assets/workflow-assets.ts#L488)）。
- 影响：每保存一次含父代理节点的工作流，就产生/复用一个 **inline parent 资产**；父代理提示词因此散落成多条资产，
  「在同一条资产上叠加版本、可回滚」的迭代语义失效（这与用户「父代理 active 提示词有且只有一份」直接冲突）。
- 处置：**父代理节点不参与角色资产登记**，改为「全节点壳」原样落库（该路径已存在：非角色节点 `shells.push(node)`，
  重建时 `isFullNodeShell` 直接还原）→ 工作流资产仍完整保存父代理节点内容，但不再产生 parent 角色资产。
  旧数据兼容：历史版本行里父代理节点仍按 roleVersionIds 引用，重建逻辑不需改。

#### D4｜父代理模板入库会新建多条父代理资产（与「唯一迭代」冲突）

- 现状：`promoteRole` 与子代理同一逻辑——内容不同即新建 standalone 资产 + 报重复检查。
- 张力：用户说「入库逻辑和子代理相同」，同时又要求「父代理提示词唯一、可迭代可回滚」。
  子代理有多个角色、多份资产是正常的；父代理全局只有一个角色，多次入库应落在**同一条资产**上才能形成版本链。
- 处置建议：父代理入库特例——**若资产库已有父代理资产，则在该资产下追加版本（Active 移到新版本）；没有才新建**。
  子代理入库逻辑不变。这是「同一条资产上的版本叠加」，与用户描述的「修改时叠加版本」一致。
- 影响：`promoteRole` 需要按 kind 分流；入库按钮在父代理模板上从「新建资产」变为「升版本」。

#### D5｜PATCH 工具可以编排父代理节点（违反「父代理不能编排自己」）

- 现状：`applyGraphOpsInPlace` 允许 `create_node kind='parent'`；`remove_node` / `update_node_data` /
  `connect_line` / `disconnect_line` 也没有父代理保护（仅 `PARENT_UNCONFIGURABLE_ROLE_FIELDS` 剥离部分字段）。
- 影响：父代理可增删自己的节点、改自己的提示词、改自己的流程连线——而父代理是否被流程线驱动，
  会直接改变它自己的执行模式（纯编排 / 编排+自执行 / 纯执行）→ 等于父代理可以重写自己的运行时角色。
- 处置：五类 op 命中父代理节点一律拒绝（新稳定码 `WF_PARENT_SELF_EDIT`，「父代理节点只能由用户手工调整」）；
  **用户手工（client）不受影响**——限制只加在父代理专用工具 `wf_graph_patch` 上。

#### D6｜外部编排提示词与新五维的冲突（第 3 批）

- `texts/parent-orchestrator.ts` / `parent-hybrid.ts`：「若编排失控或确认无法继续，即终止运行」→ 改为放置暂停门（裁决 7）；
- 同处「可重新尝试激活该节点一次，若仍失败则询问用户」→ 改为「失败重试受 retryLimit 约束；重新调度是另一回事」（裁决 4）。

#### D7｜`retryLimit` 语义（第 4 批）

- 现状：`attempts` 计数与 `retryLimit` 同时覆盖「失败重试」与「重新调度已完成节点」；
  `attempt > effectiveRetryLimit + 1` 抛 `WF_RETRY_LIMIT`（默认每节点 4 次）。
- 处置：已完成节点（上次结算为 ok）再次调度时**不递增失败重试计数**，单独累计「重新调度次数」并仅受
  `GLOBAL_RUN_CALL_LIMIT` 约束；失败/中断后的再次启动才受 `retryLimit` 限制。

### 6.3 需要拍板的两点（其余按上表执行）

1. **D3**：父代理节点改为「全节点壳」存储、不再登记角色资产 —— 确认？
2. **D4**：父代理模板入库「命中已有父代理资产则叠加版本，否则新建」——确认？（这是唯一性的必要条件；
   若不接受，则需接受资产库出现多条 parent 资产，仅靠 D2 的召回限制兜底）

### 7.4 关键裁决与红线（不得偏离）

- 阻塞一律**暂停**（插 pause 节点 → 推进即 paused），不终止；部分阻塞先做完无影响任务。
- `retryLimit` 只限制失败重试，不限制重新调度已完成节点。
- 渐进式改图是**软限制**（提示词层，不做护栏），优先改近邻节点。
- 任务：图上已有准确任务则核对、不重复发布；没有才由父代理经 `wf_send_message` 发布。
- 父代理提示词**不得被 catalog 召回**（三种来源全禁）。
- 父代理节点**不登记角色资产**；父代理模板入库**命中唯一资产则叠加版本**。
- PATCH 工具（`wf_graph_patch`）**不得编排父代理**（五类 op 全禁，`WF_PARENT_SELF_EDIT`）；用户手工改图不受限。
- 错误措辞红线：不得引导子代理使用 `wf_run_node`（子代理没有该工具）。
- Team 判据一句话进 systemPrompt；图硬规则/写图契约留在按需召回。

### 7.5 关键事实（勿重复实测）

- **暂停门**：`wf_run_node(pause 节点 id)` → run 置 `paused`、写 `resumeFromNodeId`、持久化，返回 `{status:'paused'}`（`runtime-execute.ts:87-99`）；pause 节点必须同时有 flow-in/flow-out。
- **instance 骨架**已含数据节点正文与全部连线（`wf-org-catalog/build.ts:52,291-316`）→ 父代理可判定「图上是否已有任务」。
- **资产列表排序**：`ORDER BY a.updated_at DESC, a.asset_id ASC` → 新入库自然置顶。
- **父代理节点落库形状**：完整节点对象；读回判据是形状（`parent` 且带 `data` 即全节点），
  旧版本行里的父代理壳（无 `data`）仍按壳从角色版本行回填 —— 不需要数据迁移。
- **父代理入库的来源绑定**：刷新为本次入库的模板 id + 指纹（不是继承 Active 行），否则
  「入库按钮锁定」（`isPromoteLocked`）会锁在旧模板上。
- 模板/资产/实例三层现状见 §六.1（无需重构）。
- 内置父代理资产 id：`role-parent-duties`（`src/host/assets/parent-duties-seed.ts`）。
- 词典值：`parentAgent` 中文「父代理」、英文 'Parent Agent'（`src/client/i18n.ts:24/556`）。
- 新增/删除源码文件后必须 `pnpm build`，否则 `build-artifacts` 门禁报产物不同步；`lib/` 子目录幽灵需手工删。

# Experience 数据结构

> 面向自主决策主体的可复用经验系统数据结构设计文档。

---

## 一、设计总则

Experience（经验）定义为：

> 面向某一自主决策主体，可在未来相似场景中复用的一条决策原则：当主体承担某种责任、处于某种情境并出现特定信号时，应在某个决策领域采取怎样的行动，同时明确哪些情况下不应迁移使用。

系统中的职责划分：

```text
Runtime
  ↓
提供客观运行事实 / Trace / Metrics

Generation Prompt
  ↓
规定“如何从运行事实中提炼经验”

Experience
  ↓
持久化为未来可复用的知识

Retrieval
  ↓
在未来任务中召回相关 Experience
```

## 二、统一 Experience 入库协议（由 wf_experience_learn 工具校检）

三类 Experience 必须使用完全相同的数据结构。

模型只负责提供以下语义字段：

```json
{
  "experiences": [
    {
      "responsibility": "...",
      "task_type": "...",
      "decision_domain": "...",
      "situation": "...",
      "trigger": "...",
      "principle": "...",
      "recommended_action": "...",
      "exclusions": [
        "..."
      ],
      "evidence": [
        "..."
      ]
    }
  ]
}
```

### 字段定义

| 字段 | 类型 | 含义 |
|---|---|---|
| `"responsibility"` | string | 当前自主主体承担的责任范围。回答“我对什么负责”。 |
| `"task_type"` | string | 轻量任务分类标签，用于结构化检索、过滤和未来分布式召回。不是具体任务名称。 |
| `"decision_domain"` | string | 经验所涉及的决策领域。回答“这是哪一类决策问题”。 |
| `"situation"` | string | 经验成立时所面对的实际情境或状态。回答“发生了什么”。 |
| `"trigger"` | string | 未来再次出现什么信号时，应当想到这条经验。回答“什么情况下应该回忆它”。 |
| `"principle"` | string | 从运行结果中抽象出的核心规律、因果关系或判断原则。回答“为什么”。 |
| `"recommended_action"` | string | 将原则转化为未来可执行的行为建议。回答“以后应该怎么做”。 |
| `"exclusions"` | array[string] | 明确哪些情况下不应直接迁移该经验，用于防止负迁移。 |
| `"evidence"` | array[string] | 支撑该经验的简短事实证据，只保留关键事实，不保存完整运行日志。 |

### 三组容易混淆的边界

| 字段 | 含义 |
|---|---|
| `situation` | 什么情况正在发生 |
| `trigger` | 出现什么信号时应该回忆经验 |
| `exclusions` | 什么情况下不要使用经验 |
| `principle` | 为什么 / 学到了什么规律 |
| `recommended_action` | 下一次具体应该怎么做 |
| `responsibility` | 主体负责什么 |
| `decision_domain` | 主体正在做哪类决策 |

这些字段不能因为语义相关就合并。

## 三、数据库表：`experience_prompt`

该表保存“经验生成策略”。

它本身不是 Experience，不参与向量检索。

```sql
CREATE TABLE experience_prompt (
    id BIGINT PRIMARY KEY AUTO_INCREMENT COMMENT 'Prompt 唯一标识',

    experience_type VARCHAR(32) NOT NULL COMMENT
        '经验主体类型：agent / team / orchestrator',

    name VARCHAR(128) NOT NULL COMMENT
        'Prompt 名称，便于管理和展示',

    description VARCHAR(512) NULL COMMENT
        'Prompt 的用途说明',

    prompt LONGTEXT NOT NULL COMMENT
        '完整的经验生成 Prompt 内容',

    prompt_version VARCHAR(32) NOT NULL COMMENT
        'Prompt 版本',

    is_active BOOLEAN NOT NULL DEFAULT TRUE COMMENT
        '是否为当前该 experience_type 使用的生效 Prompt',

    created_at DATETIME(6) NOT NULL COMMENT
        '创建时间',

    updated_at DATETIME(6) NOT NULL COMMENT
        '最后更新时间',

    INDEX idx_experience_prompt_type (
        experience_type
    ),

    INDEX idx_experience_prompt_active (
        experience_type,
        is_active
    )
) COMMENT='Experience 生成 Prompt 配置表';
```

### 约束

业务上必须保证：

- `agent` → 最多 1 个 active Prompt
- `team` → 最多 1 个 active Prompt
- `orchestrator` → 最多 1 个 active Prompt

Prompt 历史版本可以全部保留，但只有一个版本 `is_active = true`。

## 七、数据库表：`experience`

这是 Experience 的核心持久化表。

### 1. 完整结构

```sql
CREATE TABLE experience (
    id BIGINT PRIMARY KEY AUTO_INCREMENT COMMENT
        'Experience 唯一标识',

    experience_type VARCHAR(32) NOT NULL COMMENT
        '经验主体类型：agent / team / orchestrator；用于分类和检索过滤',

    responsibility VARCHAR(255) NOT NULL COMMENT
        '主体承担的责任范围：我对什么负责',

    task_type VARCHAR(128) NOT NULL COMMENT
        '轻量任务分类标签；用于结构化检索，不保存具体任务上下文',

    decision_domain VARCHAR(255) NOT NULL COMMENT
        '经验涉及的决策领域：正在解决哪类决策问题',

    situation TEXT NOT NULL COMMENT
        '经验成立时所面对的实际情境或状态',

    trigger TEXT NOT NULL COMMENT
        '未来执行中什么可识别信号应该触发该经验的回忆',

    principle TEXT NOT NULL COMMENT
        '从执行结果中抽象出的核心规律、因果关系或判断原则',

    recommended_action TEXT NOT NULL COMMENT
        '未来遇到类似情况时推荐采取的具体行动',

    exclusions JSON NOT NULL COMMENT
        '不应直接迁移使用该经验的条件列表',

    evidence JSON NOT NULL COMMENT
        '支撑该经验的关键事实列表；不是完整运行日志',

    task_retrieval_text TEXT NOT NULL COMMENT
        '系统生成的任务侧检索文本；由已有语义字段组合生成，不由模型直接提交',

    task_embedding VECTOR COMMENT
        '任务侧检索向量；具体 VECTOR 类型和维度按当前向量数据库实现',

    decision_retrieval_text TEXT NOT NULL COMMENT
        '系统生成的决策侧检索文本；由决策相关字段组合生成',

    decision_embedding VECTOR COMMENT
        '决策侧检索向量',

    embedding_model VARCHAR(128) NULL COMMENT
        '生成向量所使用的 Embedding 模型名称',

    embedding_dimension INT NULL COMMENT
        '向量维度；即使可以从向量本身推导，仍保留用于模型/数据兼容性记录',

    source_run_id VARCHAR(128) NOT NULL COMMENT
        '产生该 Experience 的原始运行记录 ID',

    generation_prompt_id BIGINT NOT NULL COMMENT
        '生成该 Experience 时使用的 Prompt ID',

    generation_prompt_version VARCHAR(32) NOT NULL COMMENT
        '生成该 Experience 时使用的 Prompt 版本',

    is_active BOOLEAN NOT NULL DEFAULT TRUE COMMENT
        'Experience 是否仍参与正常召回；删除/归档优先通过该字段完成',

    created_at DATETIME(6) NOT NULL COMMENT
        'Experience 创建时间',

    updated_at DATETIME(6) NOT NULL COMMENT
        'Experience 最后更新时间',

    INDEX idx_experience_type_active (
        experience_type,
        is_active
    ),

    INDEX idx_experience_task_type (
        task_type
    ),

    INDEX idx_experience_decision_domain (
        decision_domain
    ),

    INDEX idx_experience_source_run (
        source_run_id
    ),

    INDEX idx_experience_generation_prompt (
        generation_prompt_id
    ),

    CONSTRAINT fk_experience_generation_prompt
        FOREIGN KEY (generation_prompt_id)
        REFERENCES experience_prompt(id)
) COMMENT='自主主体可长期复用的 Experience 知识表';
```

> `"VECTOR"` 在这里表示逻辑向量字段。实际项目使用 pgvector、MySQL Vector、Milvus、Qdrant 或其他方案时，按当前工程的向量存储方式替换即可。`embedding_dimension` 单独保存。

## 八、Experience 字段分层

为了避免把所有字段理解成同一种东西，可以明确分层。

### 1. Identity

- `id`
- `experience_type`

回答：

> 这是什么经验？属于谁？

---

### 2. Semantic Core

- `responsibility`
- `task_type`
- `decision_domain`
- `situation`
- `trigger`
- `principle`
- `recommended_action`
- `exclusions`

这些字段才是 Experience 本身。

其中：

```text
responsibility
    ↓
主体负责什么

task_type
    ↓
这属于哪类任务

decision_domain
    ↓
涉及哪类决策

situation
    ↓
什么状态下成立

trigger
    ↓
什么信号触发回忆

principle
    ↓
真正学到了什么

recommended_action
    ↓
以后怎么做

exclusions
    ↓
什么时候不要这样做
```

---

### 3. Evidence

- `evidence`

它负责回答：

> 为什么相信这条经验？

但 Evidence 不应该成为 Experience 的主体。

---

### 4. Retrieval Projection

- `task_retrieval_text`
- `task_embedding`
- `decision_retrieval_text`
- `decision_embedding`
- `embedding_model`
- `embedding_dimension`

这一层全部服务于“找经验”。

它们不是经验本体。

建议系统生成两个检索文本：

任务侧：

```text
responsibility
+
task_type
+
situation
+
trigger
```

形成：

```text
task_retrieval_text
```

决策侧：

```text
decision_domain
+
principle
+
recommended_action
+
exclusions
```

形成：

```text
decision_retrieval_text
```

因此已经完全不需要 `task_context`(删除该字段);

经验生成模型也不需要直接产生这两个 Retrieval Text。

---

### 5. Provenance

- `source_run_id`
- `generation_prompt_id`
- `generation_prompt_version`

这一层回答：

> 这条经验从哪里来？当时依据什么生成规则？

---

### 6. Lifecycle

- `is_active`
- `created_at`
- `updated_at`

负责经验生命周期。

---

## 九、Experience 生成时模型与数据库的责任边界

最终实现时建议严格遵循下面的边界：

模型提交：

```text
responsibility
task_type
decision_domain
situation
trigger
principle
recommended_action
exclusions
evidence
```

系统自动补充：

```text
experience_type
source_run_id
generation_prompt_id
generation_prompt_version
created_at
updated_at
is_active
```

系统自动生成：

```text
task_retrieval_text
decision_retrieval_text
task_embedding
decision_embedding
embedding_model
embedding_dimension
```

这样可以避免模型伪造 provenance（来源信息）、Prompt 版本和生命周期状态。

## 十、 `wf_experience_learn` 工具与这套结构的对应关系（原 `wf_experience` 工具更名）

仍然采用之前确定的单工具、双态调用：

### 初始化（第一次调用传“空集”和类型参数调用，召回 对应的经验生成 prompt）

```text
type = agent / team / orchestrator（子代理固定只能传 agent，父代理可以根据实际任务情况选择）
wf_experience_learn([])
```

系统：

1. 识别当前主体类型
2. 找到该类型唯一 Active Prompt
3. 返回 Prompt
4. 在当前执行上下文记录：
   - `generation_prompt_id`
   - `generation_prompt_version`
   - `experience_prompt_initialized = true`（每个代理的运行实例的每个 experience_type 第一次调用后将相应的状态标记为 true，确保在经验生成前召回了相应prompt）

### 提交（第二次及之后调用传相应字段将经验入库）

```json
type = agent / team / orchestrator（只有对应的类型 experience_prompt_initialized 标记为 true 后传入实际内容才能正常入库）
wf_experience_learn([
    {
        "responsibility": "...",
        "task_type": "...",
        "decision_domain": "...",
        "situation": "...",
        "trigger": "...",
        "principle": "...",
        "recommended_action": "...",
        "exclusions": [],
        "evidence": []
    }
])
```

系统自动执行：

```text
初始化状态检查
    ↓
JSON Schema 校验
    ↓
字段长度 / 内容约束校验
    ↓
生成 task_retrieval_text
    ↓
生成 decision_retrieval_text
    ↓
生成 embedding
    ↓
同 experience_type + is_active=true
进行相似度检查
    ↓
similarity >= 0.8
    → duplicate
    ↓
否则
    → create
```

重复判断只做最简单的一件事：

> 同一 `"experience_type"` 下，如果语义核心的向量相似度 ≥ 0.8，则认为是近似重复经验，不新增。

重复判断使用 `principle` + `recommended_action` 建立向量进行相似度检查：

而不是：

- `evidence`
- `source_run_id`
- 具体项目名称
- 具体执行细节

这样可以避免同一个经验因为不同项目、不同运行实例而重复进入数据库。

# Experience 权重与评价闭环 V1 开发方案

> 本文是 **Experience V1 基础实现完成后的第二阶段开发方案**。
>
> 前置设计以已经冻结的 Experience V1 Prompt、`experience_prompts`、`experiences` 新表结构、`wf_experience_recall` / `wf_experience_learn` 工具协议为准。
>
> 本阶段只负责把 Experience 从“可生成、可存储、可召回”扩展为：
>
> `Recall → Usage → Feedback → Evaluation → Statistics → Trust → Recall`
>
> 最终形成完整的长期经验自迭代闭环。

---

## 3. 核心架构原则

### 3.1 Experience 本体与长期 Trust 必须分离

`experience` 只表达：

> 我学到了什么。

不重新加入：

```text
weight
utility
confidence
use_count
```

这些动态字段。

权重相关信息属于派生状态。

---

### 3.2 Evaluation 是历史事实，Statistics 是派生结果

正确的数据关系：

```text
Experience
   │
   ├── Usage #1
   │      └── Evaluation #1
   │
   ├── Usage #2
   │      └── Evaluation #2
   │
   └── Usage #3
          └── Evaluation #3

Evaluation *
      ↓
Statistics
      ↓
Trust
```

因此：

- Evaluation 不覆盖历史。
- Statistics 可以随时从 Evaluation 重建。
- Trust 算法未来变化时无需迁移 Experience 内容。
- 删除/损坏 Statistics 不应破坏经验历史。

---

## 4. 统一评分协议 V1

### 4.1 五级语义锚点

Experience Evaluation 所有离散评分都必须使用**五级语义锚点**。

允许值：

```text
0
0.25
0.50
0.75
1.00
```

不要允许任意连续小数。

原因：

> 0.73、0.81 这种数字表达了不存在的精度，也让模型重新回到“凭感觉给数字”的状态。

---

## 5. 四个评价维度

本阶段统一使用四个维度。

### 5.1 Fit / 适用性

范围：

```text
0 ～ 1
```

问题：

> 这条 Experience 是否真正适用于当前场景？

锚点：

| 值 | 统一定义 |
|---:|---|
| 0 | 基本不适用，关键条件不成立 |
| 0.25 | 只有局部关联，关键适用条件不足 |
| 0.50 | 部分适用，需要明显调整后才能使用 |
| 0.75 | 大部分关键条件成立，可直接参考 |
| 1.00 | 与当前决策情形高度匹配，可直接迁移其判断 |

Fit 主要用于**当前使用事件的归因与召回质量分析**，不应成为长期 Trust 的主要正向来源。

原因：

> 向量相似度已经负责“当前语义相关性”。

---

### 5.2 Decision Effect / 决策效果

范围：

```text
-1 ～ +1
```

这是整个评价体系最核心的价值轴。

统一锚点：

| 值 | 统一定义 |
|---:|---|
| -1.00 | 明显把决策带向错误方向，造成重大风险/返工/损失 |
| -0.50 | 对决策造成明显负面影响，但未形成严重后果 |
| 0.00 | 与“不使用该 Experience”相比，没有可归因的实质差异 |
| +0.50 | 对决策产生明显正面帮助，降低风险/成本/返工或提高结果质量 |
| +1.00 | 对关键结果具有决定性帮助；没有该 Experience，决策很可能明显变差 |

必须强调：

> Decision Effect 不是“我有多喜欢这条经验”，而是“使用这条经验相比不使用它，决策/结果实际改变了多少”。

这使评价天然具有反事实参照。

---

### 5.3 Information Gain / 信息增益

范围：

```text
0 ～ 1
```

问题：

> 这条 Experience 在这次使用中提供了多少真正具有区分度的决策信息？

锚点：

| 值 | 统一定义 |
|---:|---|
| 0 | 几乎是常识/空泛正确话术，不提供额外决策信息 |
| 0.25 | 提供很小的补充信息 |
| 0.50 | 提供一个有用但不强的区分条件 |
| 0.75 | 明显改变决策边界或行动选择 |
| 1.00 | 提供关键、非显然、强区分性的决策规则 |

该维度专门解决：

> “泛化程度很高、每次都很正确，但实际上没告诉 Agent 任何新东西”的庸俗 Experience。

---

### 5.4 Causal Confidence / 因果归因置信度

范围：

```text
0 ～ 1
```

问题：

> 我有多大把握认为这次效果确实来自 Experience，而不是 Agent 自身操作、外部系统或随机因素？

锚点：

| 值 | 统一定义 |
|---:|---|
| 0 | 无法判断是否由 Experience 导致 |
| 0.25 | 只有非常弱的主观猜测 |
| 0.50 | 有一定证据，但存在明显混杂因素 |
| 0.75 | 有较强证据表明 Experience 实际影响了决策 |
| 1.00 | 存在直接归因/明确反事实证据 |

该维度必须严格区分：

```text
Runtime Fact
    ≠
Experience Effect
```

---

## 6. 评分者尺度统一机制

### 6.1 模型只允许选择锚点
 
Feedback Schema 不允许：

```json
{"utility": 0.83}
```

只能：

```json
{
  "fit": 0.75,
  "decision_effect": 0.50,
  "information_gain": 0.75,
  "causal_confidence": 0.75
}
```

服务端必须 deterministic reject 非法值：

```text
WF_BAD_ARGS
```

---

### 6.2 记录评分者，但 V1 不做评分者修正

Evaluation 必须记录：

```text
evaluator_subject_id
evaluator_model
```

目的不是立刻做校准，而是为未来：

```text
Rater Calibration
Hierarchical Bayesian Calibration
```

留下数据。

V1：

> 不对不同 Agent 的历史评分进行人为归一化。

因为没有足够样本时，校准器本身更容易制造噪声。

## 9. Evaluation 聚合算法

### 9.1 单次评价的有效权重

设：

```text
F = Fit
C = Causal Confidence
```

则：

```text
evaluation_weight =
    F × (0.25 + 0.75 × C)
```

解释：

- Fit = 0 → 本次评价对长期经验价值不起作用。
- Causal Confidence = 0 → 仍保留 25% 的最小统计权重，不完全丢弃。
- 高 Fit + 高 Confidence → 最大有效权重。

---

### 9.2 单次价值贡献

设：

```text
D = Decision Effect
I = Information Gain
```

正向收益：

```text
positive_effect =
    D × (0.5 + 0.5 × I)
```

但对负向效果不削弱：

```text
effective_effect =
    D >= 0
      ? D × (0.5 + 0.5 × I)
      : D
```

设计目的：

> “泛化正确但信息量低”的 Experience，其正向收益受到抑制。

同时：

> “有害 Experience”不能因为它本身很空泛就获得减刑。

---

## 10. 统计估计：不要直接取平均

### 10.1 中性先验

新经验初始：

```text
prior_mean = 0
prior_strength = 3
```

不要让：

```text
第一次 +1
```

立刻得到：

```text
value = +1
```

---

### 10.2 Effective sample size

定义：

```text
n_eff = Σ evaluation_weight
```

它不是简单的使用次数。

高置信、高适用评价贡献更大。

---

### 10.3 收缩后的经验价值

设历史评价为：

```text
v_i
```

对应统计权重：

```text
w_i
```

则：

```text
empirical_value =
    Σ(w_i × v_i)
    /
    (prior_strength + Σw_i)
```

先验均值为 0，因此无需额外项。

最终：

```text
empirical_value ∈ [-1, +1]
```

---

## 11. 证据强度

经验价值和“我有多确定这个价值”必须分开。

定义：

```text
evidence_strength =
    1 - exp(-n_eff / 8)
```

大致行为：

```text
n_eff 小
    → 证据很弱

n_eff ≈ 8
    → 证据开始稳定

n_eff ≈ 16
    → 高可信

n_eff 更大
    → 逐步饱和
```

这可以解决：

```text
第一次 +1
```

导致新经验突然霸榜的问题。

---

## 12. 稳定性

对历史 `effective_effect` 计算加权方差：

```text
variance
```

标准差：

```text
sigma = sqrt(variance)
```

定义 V1：

```text
stability =
    clamp(1 - sigma, 0, 1)
```

含义：

- 全部评价接近 → Stability 高。
- 正负评价剧烈冲突 → Stability 低。

例如：

```text
+0.8
+0.7
+0.9
+0.8
```

稳定。

而：

```text
+1
-1
+1
-1
```

价值均值可能接近 0，但更重要的是：

```text
stability 很低
```

意味着：

> 这条 Experience 的适用行为可能高度不稳定。

---

## 13. Harm Rate

保留单独统计：

```text
harm_rate
```

其中只统计：

```text
effective_effect < 0
```

的有效评价比例。

建议同时记录：

```text
harm_count
harm_rate
harm_severity
```

其中：

```text
harm_severity =
    Σ(w_i × max(-v_i, 0))
    /
    Σw_i
```

用途：

- Recall 降权
- GUI 管理
- 后续归档候选
- 未来风险治理

V1 不自动删除 Experience。

---

## 14. Experience Trust

不直接存一个永久 `weight`。

先形成中心化质量信号：

```text
quality_signal =
    empirical_value
    × evidence_strength
    × (0.5 + 0.5 × stability)
```

范围：

```text
[-1, +1]
```

再定义用于展示/管理的：

```text
trust =
    0.5 + 0.45 × quality_signal
```

范围：

```text
[0.05, 0.95]
```

### 解释

```text
0.5
```

表示：

> 没有足够证据，当前保持中性。

不是：

> 这条经验有 50% 概率正确。

---

## 15. 为什么不直接把 Trust 作为 Recall 分数

不能：

```text
final_score =
    similarity + trust
```

也不能：

```text
final_score =
    0.5 × similarity + 0.5 × trust
```

否则会出现：

```text
低相关 + 高 Trust
>
高相关 + 中 Trust
```

这是本系统明确禁止的。

---

## 16. Stage 1：Candidate Generation

正常情况下：

```text
Embedding Query
    ↓
Cosine Similarity
    ↓
Top K
```

建议：

```text
K = 30
```

V1 先固定为 30，便于测试。

此阶段：

> Trust 完全不参与。

---

## 17. Stage 2：Bounded Trust Re-ranking

把 cosine：

```text
[-1, +1]
```

归一化为：

```text
sim01 = (cosine + 1) / 2
```

把：

```text
quality_signal ∈ [-1, +1]
```

保留中心化形式。

定义：

```text
adjusted_relevance =
    sim01 ×
    (1 + β × quality_signal)
```

建议：

```text
β = 0.20
```

因此 Trust 对相关性的最大影响只有：

```text
+20%
```

或：

```text
-20%
```

绝不允许出现：

```text
+100%
+300%
```

级别的直接碾压。

---

## 18. 为什么是乘法而不是加法

采用：

```text
similarity × bounded quality adjustment
```

而不是：

```text
similarity + quality
```

原因：

> Quality 是对候选相关性的微调，而不是第二个独立的召回轴。

这样可以保持：

```text
相关性 = 主导因素
Trust = 修正因素
```

---

## 19. MMR

Trust 调整完成后，再进入 MMR。

明确使用命名参数，避免 λ 语义混乱：

```text
relevance_weight
diversity_weight
```

推荐 V1 初值：

```text
relevance_weight = 0.40
diversity_weight = 0.60
```

即：

> 继续保留当前系统偏向高多样性的行为。

MMR：

```text
MMR(i) =
    relevance_weight × adjusted_relevance(i)
    -
    diversity_weight × max_similarity_to_selected(i)
```

注意：

> Trust 只修改 `adjusted_relevance`，不修改 diversity term。

这是为了防止：

> 高 Trust 的某一类经验因为多个相似实例重复出现而霸占整个 Recall 列表。

> 最终经过 MMR 重排序后召回前 RANK 15 的候选经验。然后 LLM 模型进行判断，再通过 id 精确召回最终所需经验。

---

## 20. 低相关经验的“硬保护”

即使 Trust 很高，也不能让明显不相关的 Experience 进入前列。

因此在 Stage 2 前保留一个 semantic floor 配置：

```text
semantic_floor
```

但不要在代码中硬编码一个未经数据验证的绝对值。

实现方式：

1. 先取得 Top K。
2. 统计实际相似度分布。
3. 用 benchmark 确定最合适的 floor。
4. 通过配置固定。

初版允许：

```text
semantic_floor = disabled
```

并优先用“Top K + bounded rerank”观察真实分布。

不要为了“保险”先写一个拍脑袋阈值。

## 24. Statistics 更新策略

不要每次评价都跑全表重算所有 Experience。

V1：

```text
Feedback
   ↓
写 Evaluation
   ↓
只增量更新对应 Experience 的 Stats
```

但必须另外提供：

```text
rebuildExperienceStats()
```

用于：

- 首次上线
- 调整算法参数
- 数据修复
- 测试
- 未来迁移

---

## 25. 为什么一定要支持 Rebuild

未来可能把：

```text
prior_strength = 3
```

改成：

```text
prior_strength = 5
```

或者：

```text
β = 0.20
```

改成：

```text
β = 0.15
```

如果 Stats 只允许增量更新：

> 历史数据无法重新解释。

因此：

```text
Evaluation
    ↓
Deterministic Aggregator
    ↓
Stats
```

必须可以完整重放。

这样可以直接：

├── trust.ts

## 28. Orchestration Experience 的特殊处理

编排经验特别适合：

```text
Experience hypothesis
        ↓
未来相似任务
        ↓
Recall
        ↓
采用策略
        ↓
Decision Effect
        ↓
跨 Run 验证
```

这里应该强调：

> “过去一次执行中看起来有效”只是一个经验假设。

长期 Trust 来自：

> 多个相似情景下重复得到相似结果。

这也是 Experience System 从“复盘仓库”升级成“经验记忆系统”的关键。

---

## 29. Agent / Team / Orchestrator 统计隔离

Experience 的长期统计应至少按：

```text
experience_type
```

隔离。

不要出现：

```text
Agent Experience
+
Team Experience
+
Orchestration Experience
```

混合计算一个 Trust。

最基本过滤：

```text
same experience_type
```

这与现有 duplicate / recall 语义一致。

## 30. Recall 的完整算法

最终推荐流程：

```text
                    Query
                      │
                      ▼
                 Embedding
                      │
                      ▼
             Semantic Top-K = 30（暂定30，后续调整）
                      │
                      ▼
       ┌──────────────────────────┐
       │ 每个 Experience          │
       │                          │
       │ cosine similarity        │
       │ empirical value          │
       │ evidence strength        │
       │ stability                │
       │ trust / quality signal   │
       └────────────┬─────────────┘
                    │
                    ▼
          bounded trust rerank
                    │
                    ▼
                   MMR
                    │
                    ▼
                 Top N = 15（暂定15，后续调整）
                    │
                    ▼
                  Usage（通过 id 精确召回）
                    │
                    ▼
                  Agent
```

## 36. 最终验收标准

本阶段只有满足以下条件才算完成。

### 评分

- Agent 不能任意输出连续评分。
- 所有评分维度拥有明确行为锚点。
- Decision Effect 使用 -1～1
- Fit / Information Gain / Causal Confidence 使用 0～1。

### 统计

- 一次评价不能直接决定长期 Trust。
- 新经验具有中性先验。
- 证据强度随样本增加饱和。
- 评分波动会降低 Stability。
- Evaluation 可以完全重放。

### Recall

- Trust 不能作为独立召回轴。
- Trust 只能在 semantic Top-K 内进行有界重排。
- Trust 最大影响默认 ±20%。
- MMR diversity 与 Trust 完全分离。
- 低相关高 Trust 不能击败明显高相关经验。

### 归因

- Runtime Failure 不自动等于 Experience Harmful。
- Causal Confidence 控制运行事实在评价中的可信程度。

### 闭环

必须能够实际完成：

```text
Capture
→ Recall
→ Usage
→ Feedback
→ Evaluation
→ Statistics
→ Trust
→ Recall
```

并且所有环节均有测试覆盖。

## 37. 本阶段一句话定义

> **Experience 的价值不是一个静态分数，而是一个由多次、统一尺度的使用评价形成的经验后验信号；Recall 中它只能作为受限的可信度修正，而不能取代语义相关性。**
